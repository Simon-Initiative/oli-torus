# MER-5865 step-4 proof-contract design read — reopened v2

## Blockers

1. **B4-C4A / B4-C12a / §3–§4 — the fixture-retained setup reference cannot supply the claimed identity triple.** The current `AutomationSetupResponse` in `assets/automation/src/systems/torus/tasks/AutomationSetupTask.ts` contains `section.slug` but no revision slug or resource-attempt GUID; the server schema in `lib/oli_web/controllers/api/automation_setup_controller.ex` matches that shape. The existing independent values for revision and attempt are read later from Delivery DOM props by `AdaptiveShadowCapture.correlate()`. Because `AutomationSetupTask.ts` is explicitly outside this ticket, retaining its raw response cannot establish the contract's section/revision/attempt triple. The C4A/C12a reference therefore does not exist as designed, and the both-sides witnesses cannot reach their stated rejection locus. Define a fixture-owned independent source that actually supplies all three fields within step-4 scope, then disclose its producer, parsing/helper, object-alias, and Playwright-process sharing.

2. **B4-ENTRY / B4-CORE / B4-REG / §1 WIRE — imports plus journal-issued sequence values do not prove that the new path is load-bearing.** A hybrid entry point can import the new driver/core, call the journal API to populate valid fence/permit seqs, pass the registry's isolated key matrix, and still let copied or residual old logic decide screen operations and transitions. ENTRY's live witness kills a pure stub that emits no fences, but not that hybrid; CORE's witness exercises only STAMP, not attribution, planner, permits, oracle, or online planner use; REG has no live-use witness at all. C16 and later file deletion remove named dependencies, not copied logic or a bypass inside the new entry point. WIRE needs branch-specific behavioral witnesses showing that bypassing/substituting each required core consumer and registry resolution turns the real switched run red while imports and journal seqs remain present.

3. **§1 EXIT-TOTAL / B4-C15 / §3–§4 / §7 — the new artifact proves oracle handling of supplied records, not total driver-exit-to-record mapping.** EXIT-TOTAL has no atomic proof-table row or stable conformance ID, and §4 has no positive/deletion/hollowing entry for the artifact itself. Saying that every class is exercised "through ... `auditRun`" permits tests to construct each operation-failure record directly; that proves `record → violation`, but not that each real driver exit emits the record. The operationFailures witness asserts that silence makes the artifact red without defining any independent exit inventory or observation that detects the silent branch. There is also a concrete zero-positive boundary in the cited spec: an open-window sealed snapshot audits only positive observed violations, so a pre-completion seal with no operation-failure record can return zero unless another invariant is added. Add a stable atomic row and a closed driver-exit inventory, and trigger each driver/journal branch upstream of record construction (or provide an independently checked exhaustive exit→constructor proof), including each completed-failure reason, freeze-timeout, seal-incomplete, closed/open pre-completion seal states, and record-deletion mutations.

4. **B4-SUITE / §1 and §3–§4 — the expected suite inventory is still self-selected at submission time.** V2 says the inventory is fixed in the gate-B submission immediately before the run, but does not derive it from the normative `npx playwright test adaptive- --reporter=line` scope or any other independently fixed discovery source. The writer can pin a one-test inventory, run that test, and satisfy exact equality and every listed witness. The self-red-team line therefore assumes the very completeness it must prove. Pin the expected file:test set from an independently specified discovery command and repository revision (or enumerate it in this contract before build), then compare that fixed set bidirectionally with execution.

5. **B4-MAN / §3 and §3.8 — manifest-v2 completeness is still unlisted, and registry metadata can common-mode with the shared extractor.** MAN's atomic claim covers only family+version(+mode) metadata. It does not carry §3.8's archive↔map↔scenario bijection, route/exclusion completeness, operation-ref resolution, or the §3.5 warning that scenario coverage alone is self-referential. A manifest and scenario that omit the same archive screen can therefore leave the proof table internally green without the separately required archive-completeness guarantee. In addition, MAN labels its check `IS` while one extractor produces both the archive facts and manifest input, and the raw-archive witness is scoped only to PRED; a common-mode family/version/mode transform survives. Add an atomic archive-completeness row and independently compare MAN metadata and route facts to the raw archive (with common-helper substitution witnesses).

6. **B4-PRED / §3–§4 and §6.3 — the raw-archive leg does not yet break helper common-mode, and the reduced scope does not name every eligible part.** The witness mutates extractor facts plus manifest data and says validation "re-reads" the raw archive, but does not require an implementation-independent parser/traversal. If validation re-reads through the same extractor or normalization helper, a helper mutation transforms all three legs consistently and passes. The reference is source-independent but not implementation-independent at the advertised scope. Separately, §6.3 names both part paths for `q:1516197466626:752` but gives only a screen and family description for `q:1516189150386:363`; arm (b)'s "exactly these named parts" is therefore not closed for that screen. Pin a separate raw-condition reader or immutable raw fragment and mutate the shared helper itself, and enumerate the second screen's exact part path and reduced predicate before gate B.

7. **§4 source-by-source matrix — mandatory evidence sources still lack the promised positive + deletion + hollowing proof.** Missing explicit source witnesses include the fixture-retained C4A/C12a original, EXIT-TOTAL artifact, CORE static/behavioral graph, REG contract matrix, raw archive, and execution of the DEL sweep itself; the DEL case tests a residual reference but not a hollow/no-op sweep that falsely reports clean. The manifest cases delete/hollow manifest expectations, not the raw-archive reference, and the operationFailures case does not exercise all ten driver emitters. The global "missing evidence = red" sentence supplies composition policy but not the source-specific rejection loci and replays required by the adopted protocol. Complete those source rows rather than treating downstream subject mutations as deletion/hollowing of their references.

## Should-fix

1. **B4-DEL / §1, §4, and §6 — the repo-wide sweep's exclusions remain deferred and therefore are not falsifiable from the contract.** The sweep excludes "doc-code fence[s]" using path rules to be stated later in gate evidence, without fixing the allowed roots/extensions or saying that this is the only exclusion. A later broad path rule could omit a production re-export or dynamic string reference while DEL reports clean. The two-stage predicate itself is sound; close the sweep now with exact included roots/reference forms and an exact, bounded documentation-only exclusion list.

2. **B4-ENTRY / B4-CORE / B4-C12b / §3 and §5 — reference classes remain inflated or compound.** ENTRY and CORE combine a static observation of the subject code with a live runRecord under one `IA` label even though those legs have different provenance and failure domains; split them when adding load-bearing witnesses. C12b compares four values from the same setup/server evidence domain and has no different source judging the aggregate distinctness property, so `IS` overstates the relationship; the server's four responses are independent runs, not independent source types. Relabel that direct cross-run comparison `CI` (or identify a genuinely different reference) and keep its mandatory force in composition.

3. **B4-FIN1 / §3 and §7 — the row still lacks an adopted spec source.** The current §3.2 requires accepted finalization and makes `already_submitted` a violation, while §3.5 calls its strengthening list complete; neither states at-most-one accepted-success finalization. V2 creates a future normative addition and then claims every row already cites a spec source. That chooses neither round 1's "cite the exact invariant" nor "narrow the witness" option. Obtain an explicit spec/human scope amendment before treating FIN1 as mandatory, or narrow the witness to the sourced `already_submitted` case.
