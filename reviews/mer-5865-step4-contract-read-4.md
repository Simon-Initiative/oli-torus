# MER-5865 step-4 proof-contract design read — reopened v4

## Blockers

1. **B4-EXIT-INV / §1, §3, and §4 — the independent inventory check is not yet a closed, falsifiable reachability proof.** V4 now distinguishes control-flow exit sites from the §3.2 record union, but “independently checked at review” does not define the code boundary, stable site identity, enumeration rule, or expected rejection locus by which the inventory is compared to the driver/fixture control flow (`mer-5865-step4-driver-swap-contract.md:48-60,120,158-163`). In particular, “rejected await” can mean every potentially rejecting await or only an explicit rejection branch, and an inventory row can name a typed producer that exists but is not reached from that site. EXIT-EM can still be made green by injecting a different path that reaches the named producer. Require exact set equality between an independently derived site list and the artifact over a closed source/call-graph scope; give every site a stable source identity and exit kind; and make the per-site injection activate that exact site and assert that its pinned producer, and no other producer, emitted before the boundary/seal. Until the site-to-producer edge itself is observed, an unrecorded or falsely pinned exit can remain green.

2. **B4-VERDICT / §1, §3, and §4 — one forced driver-flag case does not prove that audit violations are the sole licensing input.** The row claims that pass/fail derives solely from `auditRun` and admits no other input, but its only witness fixes `auditRun` positive and the driver flag green (`mer-5865-step4-driver-swap-contract.md:26-31,67-68,108,174-182`). A verdict such as `auditZero || alternateOverride` passes that witness whenever the unmentioned override is false, yet can later license a violated run when it is true. B4-C16 statically excludes the shipped ledger and shadow projection, and the named witness excludes the driver flag, but nothing closes the verdict's input domain generally. Add an IA/static data-flow or API-shape witness showing that the assertion boundary accepts only `auditRun`'s violations (or exhaustively enumerate every available non-audit signal), plus a mutation that puts each possible alternate signal in its licensing state while `auditRun` returns a violation. Without that closure, `SOLELY` is broader than the evidence.

3. **B4-SUITE / §1, §3, §4, and §6.7 — the additive manifest self-selects new coverage, and Playwright discovery does not preserve intra-test generated-case cardinality.** The pre-step-4 artifact closes deletion or rename of discovered legacy test identities, but the writer can omit a required new step-4 witness from the additive manifest; exact expected↔executed equality then remains green because no independent mapping requires every B4 row and §4 semantic mutation to appear in that manifest (`mer-5865-step4-driver-swap-contract.md:32-40,126,183-188,244-246`). There is also a concrete mismatch in the cited enumerator validation. Canonical `playwright --list` reports the loop at `adaptive-oracle.spec.ts:624` as sixteen separate tests, but reports the loop at `adaptive-oracle.spec.ts:1799` as one outer test, `every disqualifying final-step target...`; removing `prev`, `first`, `last`, or the explicit id from that inner array changes coverage without changing the discovered file:test identity. The verified discovery output is 123 tests, while the source has 108 `test(` occurrences; only the first cited loop accounts for generated Playwright identities. Require a contract-derived, bidirectional mapping from every mandatory conformance ID and every closed witness variant to a discovered test or separately reported case ID. Data-driven cases whose cardinality matters must either be separate named Playwright tests or emit a case inventory compared exactly to a pre-fixed expected set. Otherwise both required new coverage and existing inner-loop cases can disappear without SUITE noticing.

## Should-fix

1. **B4-C4A / §4 — the freeze witness covers replacement, but not mutation of the retained node itself.** The normative timing and the post-snapshot navigation/DOM-replacement case discharge the round-3 request as written (`mer-5865-step4-driver-swap-contract.md:114,146-152`). The cited precedent currently parses `data-react-props` and copies its three primitive fields into a new object (`AdaptiveShadowCapture.ts:188-210`), which is safe from later attribute changes. The future witness, however, can pass if an implementation retains an `ElementHandle` to the original node: replacing the DOM leaves that detached node unchanged, while an in-place `data-react-props` mutation on the same node can change a later read and launder a later finalization. Add a same-node, same-page attribute-mutation witness after the capture; the retained value triple must remain unchanged and a finalization matching only the mutated props must be rejected.

2. **Template §3 / document shape — all seven sections exist, but the contract is not the short, minutes-reviewable artifact the adopted process requires.** The process consult calls for a one-page, rigid contract and identifies reviewer fatigue as a false-green risk (`mer-5865-process-consult.md:82-100,102-115`). V4 is 265 lines, and §4 carries many compound prose witnesses rather than a compact row-to-witness/rejection-locus/status matrix; its heading also says each witness records its latest replay even though no build exists and no replay statuses are recorded (`mer-5865-step4-driver-swap-contract.md:136-197`). Keep the seven-section normative core compact, move fold history and detailed source narratives to an appendix or gate-evidence artifact, and represent each planned witness with its conformance ID, mutation/case ID, expected locus, and `PENDING-BUILD` status. That makes omissions and later drift mechanically visible without weakening the contract.
