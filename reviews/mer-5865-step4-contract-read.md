# MER-5865 step-4 proof-contract design read

## Blockers

1. **§1 / B4-DEL — the final predicate can turn green before the licensed deletion outcome is proved.** `GATE-B GREEN` contains only `SUITE ∧ DIFF ∧ ACCEPT ∧ FAIL-MAP`; B4-DEL is described as post-green work outside that formula. The stated gate scope nevertheless includes deletion of the three old-walker files. Moreover, the proposed grep establishes only that no spec imports them, not that the files were deleted or that no non-spec production path still references them. The contract needs a two-stage predicate: a pre-deletion swap predicate that authorizes deletion, followed by a gate-B closure predicate that includes exact file absence plus repository-wide residual-reference checks. As written, the gate can close while a licensed outcome remains unproved.

2. **§1 and B4-C15 / §4 — `FAIL-MAP` is vacuous on all-green acceptance runs and the one poisoned-answer witness does not prove the universal claim.** The formula quantifies over non-green exits "across all runs"; canary + 3 green runs contain no such exits, so that conjunct passes without evidence. The witness plan exercises only a poisoned-answer failure, while §3.2 defines ten closed driver-operation failure variants and also defines completed-failure finalization, freeze-timeout, seal-incomplete, and pre-completion seal paths. A missing record for any unexercised exit can therefore survive the proposed evidence. B4-C15 needs an independently closed exit inventory and either an exhaustive/total mapping proof or a gate-entry replay for every exit class, including completed-failure and sealing branches; the gate predicate must require that proof artifact rather than quantify only over exits that happened in the four acceptance runs.

3. **§3 bidirectional-coverage assertion — the table omits mandatory §7-step-4 guarantees for the registry, new driver, manifest v2, and actual spec switch.** B4-C16 proves absence of shipped-ledger/shadow acceptance dependencies, but absence of an old dependency does not prove that the switched spec invokes the new driver or that the driver consumes the committed journal/attribution/planner/permits/oracle core. B4-PRED covers only two grading-predicate areas; it does not prove manifest-v2 family+version(+mode) metadata or fail-closed registry resolution. B4-DIFF is explicitly corroborating and cannot supply these missing license terms. Add atomic mandatory rows, with real §3.1/§3.6/§7 sources and positive/red witnesses, for the switched entry point, new-driver core wiring, registry key/resolution contract, and manifest-v2 registry metadata. The current assertion that every step-4 obligation maps to a row is false.

4. **B4-SUITE / §1, §3, and §4 — `SUITE` can pass with an empty or silently reduced test set.** The subject and reference are both the reporter's enumeration of whatever ran; there is no independently pinned inventory of what the strict subset must contain and no bidirectional set comparison. A runner that executes one passing test can truthfully report that exact one-test list and satisfy the current term. The witness plan also has no B4-SUITE positive, deletion, hollowing, or cardinality-preserving substitution witness. B4-SUITE is a sound writer-minted ID, but it needs an independent expected inventory, exact set equality against executed file:test identities, and a replacement witness that swaps one required test for an unrelated passing test while preserving count.

5. **B4-C4A and B4-C12 / §3 and §4 — the one-producer restriction is stated but not proved against its defining common-mode failure.** The reference is described as setup responses serialized into `runRecord` by the driver, yet the contract does not retain or compare an immutable setup-source value outside the driver-produced record. The listed correlation-field substitution appears single-sided; it does not replace both the setup/run identity and finalization identity with the same wrong values, nor make the setup side derive from the finalization record. Such a cardinality-preserving common-mode mutation retains exact equality and pairwise distinct run tuples. The proof needs provenance that distinguishes serialization from manufacture, plus witnesses for derivation from the judged finalization and same-wrong-value substitution on both sides. Otherwise B4-C4A's central clause is only prose.

6. **B4-PRED / §3, §4, and §6.3 — the disclosed shared extractor is disqualifying, and the reduced-scope arm is not closed.** The row labels archive facts versus manifest validation `IS` while disclosing that one extractor produces both archive facts and manifest input. That is exactly the common-mode producer that can transform source predicate semantics and expected manifest semantics together; local validation would still pass. The semantic witnesses cover unknown operators and type mismatch, not common-mode or cardinality-preserving predicate substitution. Separately, §6.3 says "those named parts" without naming the parts or stating the reduced matcher predicate, assigns the decision to step 5, and allows it until C1. B4-PRED requires the step-4 live contract to contain the exact predicate or the explicit reduced scope, not a future-owned placeholder. Pin the raw independent source/provenance and its semantic comparison, and enumerate the reduced scope now if that arm remains available.

7. **B4-DIFF / §6.1 — the driver-evidence retirement is an open-ended delta class.** The allowlist moves from 65 muted checks to an "archive-computed inventory" of 22 classes, but it does not give an element-level mapping, define whether 65 and 22 are counts of the same unit, or bound which projection differences retirement permits. "Class ceases to exist" is not an independent bound or an expiry; it can mask missing permits/plans/acks as retirement. B4-DIFF is a sound corroborating ID, but every retired item needs a closed old-evidence → live-oracle-predicate mapping and any unmapped occurrence must be red. The allowance should expire at gate B once that mapping has been consumed.

8. **§4 / B4-STAMP, B4-C5, B4-C8, B4-C12, B4-DIFF, and B4-DEL — the promised witness matrix is materially incomplete.** The heading promises positive + deletion + hollowing for every mandatory source, but there are none for suite output, differential evidence, run-distinctness evidence, seam-retirement evidence, or post-deletion repository state; `runRecord` deletion/hollowing covers only a permit and not visits, receipts, or operation-failure completeness. B4-STAMP exercises the two orderings only for entry/readback examples, not for each check/ack permit boundary, and the saved-barrier case does not cover both the readback fence and check-permit boundary. B4-C5 moves a mint after its consuming evaluation but not before the first rotation evaluation; B4-C8 lacks a cardinality-preserving visit/root ownership swap. Complete the source-by-source matrix and exercise both interleavings at every ordering-sensitive fence through the same decision entry point.

## Should-fix

1. **§3 B4-C3, B4-C5, B4-C8, B4-C12, B4-C15, and B4-DIFF / §5 — the reference taxonomy does not conform to the adopted three-class protocol.** B4-C3's freeze flavor is produced and judged by the journal; B4-C5's mint edges are derived from journal records and journal order; and B4-C8's lineage is derived from journal records plus journal-issued fences. Those are capture-internal relationships, not `IA`. B4-C12 combines setup-to-finalization correlation with same-producer cross-run distinctness under one `IS` label and should be split. B4-C15 uses `composition` and B4-DIFF uses `C` in the Class column, although the only permitted classes are `IA`, `IS`, and `CI`; `C` is a role, not a class. Consequently §5's statement that the only CI evidence retires with the shadow seam is also false. Relabel/split the rows so the mandatory status comes from composition, not an inflated independence label.

2. **§4 live-journal witness — duplicate accepted finalization has no cited rejection rule.** §3.2 explicitly makes `already_submitted` a violation, but the cited source does not state that two independently accepted-success finalization records are themselves a violation. The witness currently conflates those cases. Cite the exact invariant that rejects duplicate accepted finalizations or narrow the witness to duplication that produces the specified `already_submitted` status.

## Summary

**Counts:** 8 blockers, 2 should-fix, 0 nits.

**Verdict:** **REDESIGN**. The page is not yet a reviewable gate-B proof design: the final predicate omits deletion closure, failure mapping and suite health can pass vacuously, mandatory step-4 swap guarantees lack rows, and the known common-mode/allowlist/interleaving paths are not closed. This verdict is design-only and is not a judgment on any future implementation or gate evidence.
