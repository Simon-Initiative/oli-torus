- [x] Checkpoint D implementation (2026-11-19):
  - Migration `priv/repo/migrations/20261119193918_convert_settings_changes_to_audit_events.exs` (generated with `mix ecto.gen.migration --no-compile`; explicit `up/0` and `down/0`; SQL only, no application modules). `up/0` takes `SHARE` on `settings_changes`, inserts one v1 `assessment_setting_changed` row per history row with a new central ID (sequence default), the original `inserted_at`, the actor (`author` → author, `instructor` → user, any other type → `unknown` with the original account ID and type in `details`), `section_id` and `resource_id` scope with the resource as entity, and the setting as one change record (`before`/`after` text values, explicit nulls kept; `password` only the redaction marker). An anti-join on `(legacy_source, legacy_id, inserted_at)` makes it restartable; reconciliation (every history row has exactly one converted row) runs before `DROP TABLE settings_changes`, and a mismatch raises and rolls back. The `resource_id` column comment is updated for converted rows.
  - `down/0` recreates `settings_changes` (original columns, `timestamptz` timestamps as the repository's `migration_timestamps` config created them, foreign keys to `resources` and `sections`), inserts the converted rows back with their original IDs, values, and times (`[redacted]` where a password was), resets the ID sequence, deletes the converted rows under `SET LOCAL oli.audit_log_allow_mutation = 'on'`, and restores the column comment.
  - Design reconciled: the setting goes into `changes` as `{key: {operation, before, after}}`, as the catalog example for `assessment_setting_changed` committed in PR-01 does, instead of `key`/`old_value`/`new_value` in `details`; the Audit Log renders change records, and the family declares no detail keys. `details` carries only the original account of an unknown user type.
