# Consistent Suppressed Unit Numbering Across Course Views - Delivery Plan

Scope and reference artifacts:
- PRD: `docs/exec-plans/current/features/consistent-container-numbering/prd.md`
- FDD: `docs/exec-plans/current/features/consistent-container-numbering/fdd.md`
- Requirements: `docs/exec-plans/current/features/consistent-container-numbering/requirements.yml` (FR-001 through FR-014, AC-001 through AC-022)

## Scope
Replace every raw-numbering read path identified in the FDD (Groups A, B, and C, plus FR-014) with the suppression-aware `display_numbering` already produced by `Oli.Delivery.Sections.DisplayNumbering.decorate_hierarchy/2`, so a given unit/module/section carries the same visible number on every in-scope surface as it does on the student Learn view. Includes one new shared primitive (`Sections.decorated_numbering_map/1`), field-level fixes to five already-decorated call sites, one additive field on the `previous_next_index` cache plus a one-time data migration for currently-affected production sections, and a closing regression/scenario pass. Out of scope: any change to how `unnumbered_unit_ids` is configured, canonical/authoring-side numbering, new UI, or frontend (`assets/src/`) code (per PRD Sections 3, 9, 10).

## Clarifications & Default Assumptions
- `Sections.decorated_numbering_map/1` is built once, in Phase 1, and treated as a stable, unchanging dependency by every later phase that needs it (Group A and Group B phases). No phase after Phase 1 should modify its signature; if a later phase finds it insufficient, that is treated as a plan deviation requiring explicit note, not a silent inline change.
- Group C fixes (FR-009, FR-012, FR-014) and Phase 1 (the shared primitive) touch disjoint files and have no dependency on each other; they are planned as parallel-safe (Parallelization Notes below).
- `lib/oli_web/live/delivery/instructor_dashboard/helpers.ex`'s `get_containers/2` already calls `Sections.get_units_and_modules_containers/1` (the function fixed under FR-005), so fixing FR-005 partially fixes one of FR-006's two call sites "for free." FR-006's other call site (`intelligent_dashboard_tab.ex`'s `fetch_dashboard_containers/1`) uses the independent `SectionResourceDepot.containers/2` query and needs its own overlay. Phase 5 bundles FR-005 and FR-006 together specifically because of this shared dependency, and Phase 5's tasks call out both call sites of FR-006 explicitly so the second one is not missed.
- Every phase's Definition of Done includes the AC-020 regression case (a section with empty `unnumbered_unit_ids` renders identically before/after) scoped to that phase's own surfaces, rather than deferring all regression coverage to the end; Phase 8 additionally runs a single consolidated regression pass across every surface fixed by Phases 2-7 together, per the FDD's Testing Strategy guidance not to accumulate all verification at the end.
- The FDD's own explicit follow-up (Section 15/16: sweep for other `Hierarchy.thin_hierarchy/3`-style "decorated data dropped by an intermediate allowlist" patterns) is planned as an explicit Phase 8 task, not left implicit, so a new finding there is evaluated against PRD scope criteria before this work item is considered closed.
- Backend-only work throughout (per PRD Section 10); no `assets/src/` changes are planned in any phase. If a later phase discovers a surface that needs a frontend change, that is a scope deviation to flag, not something to silently implement.
- Phase 7's data migration follows [fly-apps/safe-ecto-migrations](https://github.com/fly-apps/safe-ecto-migrations) practices (FDD Section 6): batched keyset pagination over `sections.id`, `@disable_ddl_transaction`/`@disable_migration_lock`, raw SQL rather than the `Section` schema, and idempotent re-run safety, rather than a single unbounded `UPDATE`, because this work item has no confirmed production `sections` row count and the guide is explicit that scale should not be assumed from a lower environment. This is a deliberate scoping decision, not the guide's heavier "separate `data_migrations` path + manual release task" recommendation, since this repository has no such convention today (confirmed against `lib/oli/release.ex`) and introducing one is out of scope here.

- Implementation note — design refinement beyond the plan's literal wording, confirmed sound by the performance review: the plan described a single SELECT per page filtered directly by `array_length(unnumbered_unit_ids, 1) > 0`. The actual implementation splits each page into two steps instead: (1) a SELECT bounded purely by primary key (`WHERE id > last_id ORDER BY id LIMIT batch_size`, no domain predicate at all), then (2) an UPDATE that applies the real `array_length(...) > 0 AND previous_next_index IS NOT NULL` predicate only within that already-bounded batch of ids. This matters because a SELECT filtered directly by the domain predicate would need to scan an *unbounded* number of rows past `last_id` to fill a page if suppressed sections are rare relative to the whole table -- defeating the point of pagination. The two-step design bounds every page's cost to exactly `batch_size` regardless of how many (or how few) sections in the whole table actually match. The performance review explicitly verified this reasoning holds. Raw SQL is via `Repo.query!/2` with parameterized `$1`/`$2` placeholders, not the `from(s in "sections", ...)` Ecto query builder syntax the plan sketched -- a raw parameterized query was simpler for this exact two-query shape and is equally safe (confirmed by the security review), so the "raw SQL, not the Ecto schema" intent from Backfilling.md is met either way.
  - [x] The actual batching logic lives in a new plain (non-`Ecto.Migration`) module, `Oli.Delivery.PreviousNextIndexBackfill` (`lib/oli/delivery/previous_next_index_backfill.ex`), with the `.exs` migration file as a thin wrapper calling `PreviousNextIndexBackfill.run/1` and logging the result.
