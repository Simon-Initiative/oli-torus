# Consistent Suppressed Unit Numbering Across Course Views - Functional Design Document

## 1. Executive Summary
`Oli.Delivery.Sections.DisplayNumbering.decorate_hierarchy/2` is the single source of truth for suppression-aware container numbering, but twelve call sites across the delivery and instructor-dashboard surfaces read raw canonical numbering instead (raw SQL over `SectionResource`, a decorated hierarchy node's canonical `.numbering` field instead of its `.display_numbering`, or a shared field-allowlist helper that strips `display_numbering` before it reaches an already-correct renderer). This design fixes all twelve by introducing one new shared primitive, `Sections.decorated_numbering_map/1`, for the SQL-based call sites (FR-001 through FR-008), and by reusing the existing `Oli.Delivery.Sections.DisplayLabels.effective_numbering/1` helper for the call sites that already hold a decorated hierarchy node but read the wrong field (FR-009, FR-012). The highest-blast-radius item, the cached `previous_next_index` structure (FR-010, FR-011), is fixed with a single additive field (`"display_numbering"`) on each cached node rather than a rewrite, because the existing rendering code (`DisplayLabels.effective_numbering/1`) already prefers that key when present — and a targeted, one-time data migration invalidates the stale cache for sections that already have suppressed units in production. FR-014 is a one-line allowlist fix in `Hierarchy.thin_hierarchy/3`'s two callers, found while verifying design assumptions for the rest of this document. No new abstractions are introduced beyond what the codebase's existing `DisplayNumbering`/`DisplayLabels`/`MinimalHierarchy` trio already provides.

## 2. Requirements & Assumptions
- Functional requirements:
  - FR-001/FR-002 (Group A): Assessment Settings, Student Exceptions, and Grade Sync must show suppression-aware container numbers, via one shared fix to `Sections.get_parent_containers_map/2`.
  - FR-003 through FR-008 (Group B): Scheduling editor, Instructor Dashboard scored/practice/survey pages + CSV export, Content "Order" column, container navigators/selectors, Student Insights heading, and the AI Dialogue course-layout context must each show suppression-aware numbers, via independent overlays of the same new `decorated_numbering_map/1` primitive onto each site's existing raw query result.
  - FR-009 (Group C): Intelligent Dashboard assessment context must read `display_numbering` instead of raw `numbering` from its already-decorated hierarchy.
  - FR-010/FR-011 (Group C, highest blast radius): Legacy Course Content / page-delivery navigation must reflect suppression-aware numbering, both in newly computed data and in data already persisted for sections that currently have suppressed units.
  - FR-012 (Group C): Student Progress breadcrumbs must read suppression-aware numbering from their already-decorated hierarchy ancestors.
  - FR-013: Sections with empty `unnumbered_unit_ids` must render identically before and after this change on every in-scope surface.
  - FR-014 (Group C, shared helper): the Instructor Page Preview outline and the student Lesson page's table-of-contents drawer must show suppression-aware numbering; both are fed by `Hierarchy.thin_hierarchy/3`, whose field allowlist currently drops `display_numbering` before it reaches an already-correct `display_numbering_or_numbering/1` consumer.
- Non-functional requirements:
  - Reuse the proven `MinimalHierarchy.full_hierarchy/1` + `DisplayNumbering.decorate_hierarchy/2` query shape rather than a new, unproven hierarchy-walking approach (PRD Section 8).
  - The `previous_next_index` data correction must touch only sections with non-empty `unnumbered_unit_ids`, must be idempotent, and must not alter any other section data (PRD Section 8, 11).
  - No frontend (`assets/src/`) changes are anticipated; the Scheduling editor fix is server-side only (PRD Section 9).
- Assumptions:
  - The twelve surfaces and A/B/C groupings (the original eleven plus FR-014, found while verifying this design) are the complete in-scope set; any further surface found during implementation is evaluated against the PRD's scope criteria and added as a new requirement rather than silently folded in.
  - `display_numbering` on a `%HierarchyNode{}` is fully absent (`nil`, not merely missing an index) for any node inside a suppressed top-level unit's subtree, and equals the canonical `numbering` (via the `:not_set` fallback) when the section has no suppressed units at all — both verified by reading `lib/oli/delivery/sections/display_numbering.ex`.
  - Every location that reads `SectionResourceDepot.containers/2`, `Sections.get_units_and_modules_containers/1`, or performs the raw `get_parent_containers_map/2` SQL join is safe to keep its existing query engine unchanged; only the numbering values attached to each result row change. This preserves each site's existing caching/performance characteristics and keeps every diff narrowly scoped to "correct the number," not "replace the query."

## 3. Repository Context Summary
- What we know:
  - `Oli.Delivery.Sections.DisplayNumbering.decorate_hierarchy/2` (`lib/oli/delivery/sections/display_numbering.ex`) walks a `%HierarchyNode{}` tree and sets `display_numbering` on each node: the canonical `numbering` when the section has no `unnumbered_unit_ids`, `nil` on every node inside a suppressed top-level unit's subtree (level AND index, not just index — confirmed by reading `display_numbering/5`'s clauses), and a re-sequenced `%Oli.Resources.Numbering{}` on every other container.
  - `Oli.Delivery.Sections.DisplayLabels.effective_numbering/1` (`lib/oli/delivery/sections/display_labels.ex:13-37`) already resolves the correct value from either a `%HierarchyNode{}` (preferring `display_numbering`, falling back to `numbering` when `:not_set`) or a string-keyed map, and — critically — for a string-keyed map it prefers a `"display_numbering"` key when present (`nil` or a `%{"level"=>, "index"=>}` map) over a flat `"level"`/`"index"` pair. This existing precedence is the basis for the FR-010/FR-011 fix (Section 4.4).

  - `Sections.get_parent_containers_map/2` and `Sections.name_with_container_label/3` (`lib/oli/delivery/sections.ex:6299-6372`) are shared by Assessment Settings (`lib/oli/delivery/settings/assessment_settings.ex:159-196`) and Grade Sync (`lib/oli_web/live/grades/grades.ex:403-412`); both read raw `SectionResource.numbering_level`/`numbering_index` via a `ContainedPage` join that picks each page's most specific (deepest) parent container.

Both `ResourceTitle.render/1` call paths are therefore fed a decorated hierarchy, so the single FR-012 fix (Group C field swap) covers both without any Group B-style overlay. ## 4. Proposed Design
### 4.1 Component Roles & Interactions
- `Oli.Delivery.Sections.DisplayNumbering` (existing, unchanged): sole authority for computing suppression-aware numbering from a section and a hierarchy.
- `Oli.Delivery.Sections.DisplayLabels` (existing, unchanged): sole authority for resolving "effective" numbering from either a `%HierarchyNode{}` or a string-keyed map, and for formatting labels. Group C fixes call `effective_numbering/1` directly; the FR-010/FR-011 fix relies on its existing map-shaped clause.
- `Sections.decorated_numbering_map/1` (new): the single new primitive. Given a `%Section{}`, returns `%{resource_id => %Oli.Resources.Numbering{}}` covering every container that has a non-nil effective numbering; suppressed containers are simply absent from the map. Built per call from `SectionResourceDepot.get_delivery_resolver_full_hierarchy/1` + `Hierarchy.flatten_hierarchy/1` (implementation note, Phase 1: the original design mirrored `fetch_ordered_container_labels/2`'s `MinimalHierarchy.full_hierarchy/1`-based approach, but a Phase 1 performance review flagged that `MinimalHierarchy.full_hierarchy/1` bypasses the Depot cache, which `.review/performance.md` §3 requires delivery code to use; `SectionResourceDepot.get_delivery_resolver_full_hierarchy/1` returns the same decorated `%HierarchyNode{}` shape from cached section resource data and also avoids a redundant `Section` re-fetch, so the implementation was switched during Phase 1 rather than carrying the anti-pattern into a function designed for higher call volume than its sibling).
- Each Group A/B call site (`Sections.get_parent_containers_map/2`, `scheduling_controller.ex`, `instructor_dashboard/helpers.ex`, `Sections.get_units_and_modules_containers/1`, `intelligent_dashboard_tab.ex`, `instructor_dashboard_live.ex` (two sites, see Section 16), `students.ex`, `dialogue/student_functions.ex`): keeps its existing raw query untouched, and overlays `decorated_numbering_map/1`'s result onto the numbering fields of its existing result rows before building any label text. `scheduling_controller.ex` and `instructor_dashboard/helpers.ex`'s single-item overlay logic look up the map through a small shared helper, `Oli.Resources.Numbering.lookup/2` (added in Phase 4 in response to a review finding that both sites independently re-derived the same nil-vs-`%Numbering{}` branching), rather than calling `Map.get/2` directly. `Sections.get_units_and_modules_containers/1` and the three `%SectionResource{}`-list call sites found in Phase 5 (`intelligent_dashboard_tab.ex`, `instructor_dashboard_live.ex` x2) share a second, list-level helper, `Sections.overlay_suppression_aware_numbering/2` (public) built on a private `overlay_numbering_index/3` (also reused by `get_units_and_modules_containers/1`'s differently-keyed private overlay), which maps `Numbering.lookup/2` over a whole list at once rather than one item at a time.
- `Hierarchy.build_navigation_link_map/1`: gains one additive field per node (`"display_numbering"`), computed once via `DisplayLabels.effective_numbering/1` on the (already-decorated) input node. No other module in the `previous_next_index` -> `Sections.build_hierarchy/1` -> `CourseContent` chain changes, because `DisplayLabels.effective_numbering/1` already prefers this key.
- A new, one-time Ecto data migration invalidates `previous_next_index` for sections with non-empty `unnumbered_unit_ids`, so they rebuild through the corrected `build_navigation_link_map/1` on next access via the existing just-in-time mechanism in `PreviousNextIndex.retrieve/2,3`.
- `Hierarchy.thin_hierarchy/3`'s two callers (`preview_page_context.ex`, `lesson_live.ex`) each add `"display_numbering"` to their existing `fields_to_keep` list. No change to `thin_hierarchy/3` itself, `outline_component.ex`, or `DisplayLabels` — the consumer already prefers this key once it survives the allowlist.

### 4.2 State & Data Flow
For Group A/B (FR-001 through FR-008), the flow per request is:
1. The call site runs its existing raw query (SQL join, `SectionResourceDepot.containers/2`, or `Sections.get_units_and_modules_containers/1`) to get candidate container/page rows exactly as it does today.
2. The call site calls `Sections.decorated_numbering_map(section)` once for the request.
3. For each row that carries a container `resource_id`, the call site looks up that id in the map:
   - present -> use the map's `level`/`index` (already suppression-aware) instead of the row's raw `numbering_level`/`numbering_index` when building any label.
   - absent -> the container is suppressed; the call site omits the numbering prefix entirely for that row, using only the container's/page's title, consistent with how Learn presents a suppressed unit.
4. No change to how "which container is the row's parent" is decided — that logic (already correct) is untouched; only the numbering values attached to the resolved parent change.

For Group C (FR-009, FR-012), the flow is unchanged except the last step: instead of reading `child.numbering` / `ancestor.section_resource.numbering_level`/`numbering_index` directly, the call site calls `DisplayLabels.effective_numbering(node)` on the `%HierarchyNode{}` it already holds (these hierarchies are already decorated upstream, confirmed in Section 3), and treats a `nil` result the same way Group A/B treats an absent map entry.

For FR-010/FR-011, `Hierarchy.build_navigation_link_map/1` computes `display_numbering` once per node from the same already-decorated input tree used to compute `"level"`/`"index"` today, and stores it alongside those fields (not in place of them). Every downstream consumer of the persisted map keeps reading `"level"`/`"index"` for structural/navigation purposes and now naturally prefers `"display_numbering"` for anything that renders a user-facing label, because `DisplayLabels.effective_numbering/1`'s map clause already checks for that key first.

### 4.3 Lifecycle & Ownership
- `decorated_numbering_map/1`'s underlying section resource data is served from the `SectionResourceDepot` cache (Phase 1 implementation change, see Section 4.1); the per-call decoration and traversal work on top of that cached data (`decorate_hierarchy/2`, `flatten_hierarchy/1`, the containers-filter/reduce) is still recomputed fresh on each call, no separate memoization layer for that in-memory step. Callers that already wrap their surface in section-level caching (e.g., via `SectionCache`) may choose to cache the map's final result the same way in a later iteration; this design does not require it to meet the stated non-functional requirements.
- `previous_next_index` ownership and its just-in-time rebuild lifecycle (`PreviousNextIndex.retrieve/2,3`, `rebuild/1,2`) are unchanged; this design only changes what gets computed the next time a rebuild happens, plus a one-time forced invalidation for currently-affected sections.

### 4.4 FR-014: Restoring `display_numbering` Through `thin_hierarchy/3`
This is the smallest fix in the design, included for completeness since it was found mid-design rather than during the original audit. `Hierarchy.thin_hierarchy/3` takes a decorated hierarchy and a `fields_to_keep` allowlist and returns a pruned copy retaining only those keys per node. Both existing callers list `"numbering"` but not `"display_numbering"` in that allowlist:

```elixir
# preview_page_context.ex (Instructor Preview) and lesson_live.ex (student Lesson TOC), both today:
["id", "slug", "title", "numbering", "resource_id", "resource_type_id", "children", "graded", "section_resource"]
```

The fix adds one string to each list:

```elixir
["id", "slug", "title", "numbering", "display_numbering", "resource_id", "resource_type_id", "children", "graded", "section_resource"]
```

`DisplayLabels.effective_numbering/1`'s existing map clause (`%{"display_numbering" => nil}` / `%{"display_numbering" => %{"level"=>, "index"=>}}`, checked before the flat `%{"level"=>, "index"=>}` fallback) then resolves correctly with no further change, exactly as it already does for every other consumer of a decorated JSON-shaped hierarchy in this codebase. Because both callers already filter to `node["numbering"]["level"] <= 3` for their own unrelated reasons (limiting depth, not suppression), and that filter reads `"numbering"` (untouched, still present), this fix has no interaction with the existing depth filter.

### 4.5 Alternatives Considered
- **Replace each Group B site's raw query with `MinimalHierarchy.full_hierarchy/1` outright**, rather than overlaying `decorated_numbering_map/1` onto the existing raw result. Rejected: several of these sites (`SectionResourceDepot.containers/2`-backed ones in particular) may already benefit from depot-level caching/optimization; replacing the query engine under six independent call sites is a materially larger, riskier change than overlaying a small lookup map onto data that is already fetched, and it does not change what is displayed differently from the overlay approach.
- **Repurpose `"level"`/`"index"` in `build_navigation_link_map/1`'s output to directly carry `display_numbering`'s (sometimes fully nil) values.** Rejected: `"level"` is consumed structurally by `PreviousNextIndex.get_closest_navigable_resource/4` to decide whether to skip a container while walking prev/next links, independent of whether that container's number is suppressed; nil-ing it out would break that skip logic for suppressed subtrees. Adding `"display_numbering"` alongside the untouched `"level"`/`"index"` keeps the two concerns (structural depth vs. displayed number) separate, as `DisplayNumbering` itself does at the `%HierarchyNode{}` level.
- **Introduce a brand-new "decorated hierarchy" abstraction shared across all twelve sites**, including the Group C ones that already hold a decorated hierarchy. Rejected: Group C sites need no new fetch at all; they already have the right data in hand and are one field-read away from correct. Forcing them through a new shared abstraction would be pure indirection with no behavioral benefit, violating the Simplicity First principle.
- **For FR-014, change `outline_component.ex`'s `display_numbering_or_numbering/1` instead of the allowlist.** Rejected: that function is already correct and is reused by other, unaffected consumers (`learn_live.ex`); the defect is entirely in what data reaches it, not in how it interprets that data. Fixing the allowlist is the smaller, more precisely targeted change and requires touching only the two actual call sites of `thin_hierarchy/3`.

## 5. Interfaces
- `Sections.decorated_numbering_map(section :: Section.t()) :: %{integer() => Oli.Resources.Numbering.t()}` (new, public, in `lib/oli/delivery/sections.ex` alongside `fetch_ordered_container_labels/2`). Absence of a key means "suppressed / no number for this container."
- `Sections.get_parent_containers_map/2` (Phase 3 implementation change: the first argument now accepts either a section id or an already-loaded `%Section{}`, `(integer() | Section.t() | nil, page_ids :: [integer()]) :: map()`, rather than only an id as originally planned -- see Section 16; both real call sites already had the struct in scope, so they were updated to pass it directly and avoid a redundant `Repo.get`, found by the Phase 3 performance review) — overlays `decorated_numbering_map/1` onto the existing raw SQL result; entries whose container is suppressed are dropped from the returned map (so `Sections.name_with_container_label/3` receives `nil` and returns the title alone, exactly as it does today for a page with no parent container).
- `Hierarchy.build_navigation_link_map/1` (existing public signature, unchanged) — each entry in the returned map gains one additive key, `"display_numbering"`, whose value is either `nil` or `%{"level" => String.t(), "index" => String.t()}`, matching the existing string-keyed shape `DisplayLabels.effective_numbering/1` already expects.
- No HTTP/API contract changes except the Scheduling editor's existing JSON response (`serialize_resource/2` in `scheduling_controller.ex`), whose `numbering_index`/`numbering_level` values change (become suppression-aware) for affected sections; the field names and types are unchanged, so the existing frontend (`ScheduleLine.tsx`, `ScheduleSlideout.tsx`) requires no code change.
- No changes to `DisplayNumbering.decorate_hierarchy/2` or `DisplayLabels`'s public functions; both are consumed as-is.
- `Hierarchy.thin_hierarchy/3` (existing public signature, unchanged) — both of its callers' `fields_to_keep` argument gains `"display_numbering"`; the function's own behavior (retain listed keys) is unmodified.

## 6. Data Model & Storage
- No schema changes. `Section.previous_next_index` (`:map`) and `Section.unnumbered_unit_ids` (`{:array, :integer}`, default `[]`) are read-only inputs to this work; neither's type or default changes.
- One new Ecto migration (no schema/DDL change, a data-only bulk update), designed against the safe-migration practices in [fly-apps/safe-ecto-migrations](https://github.com/fly-apps/safe-ecto-migrations) (`README.md`, `Anatomy.md`, `Backfilling.md`):
  - **Lock profile.** A plain `UPDATE` acquires only a `ROW EXCLUSIVE` lock on the matched rows (per the guide's Postgres lock-conflict reference), not an `AccessExclusiveLock` on the table the way `ALTER TABLE`/non-concurrent `CREATE INDEX` would; unrelated rows and unrelated queries are unaffected regardless of how this migration is structured. The actual risk is the filter itself: `array_length(unnumbered_unit_ids, 1) > 0` has no supporting index, so finding matching rows requires a sequential scan of the full `sections` table, and this work item has no way to confirm the current production row count. Backfilling.md is explicit that assumptions about scale ("10 records in dev, 1 billion in production") should not drive the implementation.
  - **Design (Backfilling.md's "Batching Deterministic Data" recipe, adapted).** Rather than one unbounded `UPDATE`, the migration paginates over `sections.id` with keyset pagination (`id > last_id ORDER BY id LIMIT batch_size`, never `LIMIT`/`OFFSET`), issuing one small batched `UPDATE ... WHERE id IN (...)` per page, throttled with a short `Process.sleep/1` between batches. Each page's query and update use raw SQL/`from(s in "sections", ...)`, not the `Section` Ecto schema, per Backfilling.md's explicit warning that a migration should snapshot the table shape at the time it was written rather than depend on the application schema, which changes independently over time. The migration sets `@disable_ddl_transaction true` and `@disable_migration_lock true` (Anatomy.md) so the batched updates are not wrapped in — and defeated by — the single enclosing transaction Ecto uses by default, and so the `schema_migrations` coordination lock is not held for the full duration of the backfill.
  - **Why not the full temporary-table pattern.** Backfilling.md's "Batching Arbitrary Data" recipe (temp table of candidate ids, upsert-based batch processing) exists for cases where a row's own columns give no stable way to know it still needs processing. That does not apply here: `unnumbered_unit_ids` is a stable, independently-set predicate (this migration never modifies it), so plain keyset pagination over `sections.id` is sufficient and simpler, consistent with the FDD's Simplicity First principle (Section 4.5's rejected-alternatives reasoning applies the same way here).
  - **Why not a separate `data_migrations` path.** Backfilling.md recommends storing data migrations separately from schema migrations and running them manually via a release task, to decouple potentially slow backfills from the automatic deploy-time migration run. This repository's `lib/oli/release.ex` has no existing `data_migrations` path or manual-run convention (confirmed by inspection), and introducing one is a repository-wide infrastructure decision out of scope for this work item. Given the batched, throttled, `@disable_ddl_transaction`-based design already keeps any single lock/statement short regardless of total row count, this migration is planned as a standard migration under `priv/repo/migrations/`, run through the existing `Oli.Release.migrate/0` path. If implementation or a production row-count check later reveals this table is large enough that even a throttled full-table sequential scan is a concern, revisit this specific decision (Section 16).
  - Idempotent (re-running is a no-op for already-nulled rows) and requires no `down/0` data restoration, since the value it clears is a derived cache that self-heals via the existing just-in-time rebuild in `PreviousNextIndex.retrieve/2,3`.

## 7. Consistency & Transactions
- `decorated_numbering_map/1` reads are not transactional; it is a read-only derived view built fresh per call, consistent with `fetch_ordered_container_labels/2`'s existing behavior. A page/container added or reordered concurrently with a request is subject to the same eventual-consistency characteristics the rest of the delivery read path already has (no new consistency risk introduced).
- The data migration is not run as one atomic statement by design (Section 6): each batch is its own small, committed `UPDATE`, so a mid-migration interruption leaves some matched sections already corrected and others not yet reached — a safe, valid intermediate state, not a partial/inconsistent one, since each row's correctness depends only on its own `previous_next_index` value. No application code runs concurrently with it that depends on `previous_next_index` staying non-nil (the just-in-time rebuild in `PreviousNextIndex.retrieve/2,3` already handles `nil` as an expected, common state).

## 8. Caching Strategy
- Group A/B sites keep whatever caching they already have on their raw query. `decorated_numbering_map/1` sources its section resource data from `SectionResourceDepot`, the same cache those sites' own `SectionResourceDepot.containers/2`-backed queries already use (Phase 1 implementation change, Section 4.1); the map's own decoration/traversal step (`DisplayNumbering.decorate_hierarchy/2` + `Hierarchy.flatten_hierarchy/1` + the containers filter/reduce) is not memoized inside `decorated_numbering_map/1` itself — it recomputes on every call.
- **Per-process caching in LiveView-based consumers (decided post-Phase-2, applies to Phases 3, 5, 6).** Rather than adding a shared `SectionCache`-style memoization layer around `decorated_numbering_map/1` (which would need explicit invalidation logic), each LiveView-based consumer computes it once per LiveView process — in `mount/3` or `handle_params/3` — and stores the result in `socket.assigns`, so repeated `handle_event`/re-render cycles within the same mounted session reuse it instead of recomputing. This requires no invalidation logic: a new page load is a new `mount/3`, which naturally recomputes against current data, so there is no risk of serving stale numbering across sessions the way a shared cache would need to guard against. This is the pattern `.review/performance.md`'s "LiveViews store only what is needed to render" guidance already implies, applied specifically to this primitive.
  - Applies to: Phase 3 (`AssessmentSettingsLive`, Student Exceptions, Grade Sync), Phase 5 (Content navigator, container navigators), Phase 6 (Student Insights).
  - Does not apply to: Phase 4's Scheduling API (`scheduling_controller.ex`) and the CSV export path (`delivery_controller.ex`) — both are Phoenix controllers, not LiveViews, so each request is already naturally one-shot with no repeated `handle_event` cycles to guard against; no socket-assigns caching is needed or possible there. Phase 6's AI Dialogue context (`student_functions.ex`) is also request-scoped, not a LiveView.
- `previous_next_index` remains the same cache it is today: computed once, persisted, invalidated on relevant content/schedule changes, and rebuilt just-in-time. This design changes only what gets computed on a rebuild and forces one rebuild for currently-affected sections via the migration.

## 9. Performance & Scalability Posture
- Group A: `get_parent_containers_map/2` currently issues one SQL query scoped to the passed `page_ids`. The fix adds one `decorated_numbering_map/1` call per invocation, which reads section resource data through `SectionResourceDepot` (cached) rather than a fresh query, plus an in-memory decoration/traversal pass. `Sections.get_assessments/2` (its main caller) already loads all graded pages for the section in the same request, so this is the same order of magnitude of data as what is already fetched, not a new scaling tier.
- Group B: each site already fetches all containers for the section (via `SectionResourceDepot.containers/2` or `get_units_and_modules_containers/1`); adding one `decorated_numbering_map/1` call per request reuses the same Depot cache those sites already read from for the underlying data, adding only the in-memory decoration/traversal pass on top. No N+1 pattern is introduced since the map is built once per request, not once per row.
- FR-010/FR-011: `build_navigation_link_map/1` already walks the full hierarchy once; computing `display_numbering` per node during that same walk (via a call already available on the node) adds O(1) work per node, not a new pass over the tree.
- The data migration's per-page query is a bounded, keyset-limited scan (`LIMIT` batch size, ordered by indexed primary key `id`), so each individual statement is fast regardless of total `sections` table size; the migration's total wall-clock time scales with the number of pages needed to scan the whole table (bounded by row count / batch size) plus the throttle delay between pages, not with the number of matched rows, which is expected to be a small fraction of all sections (only those using the suppression feature). The migration logs the total number of rows updated so an unexpectedly large blast radius is visible after it runs (Section 11).

## 10. Failure Modes & Resilience
- If `decorated_numbering_map/1`'s hierarchy build fails for a section (e.g., transient DB error, Depot initialization failure), the failure surfaces the same way it already does for other `SectionResourceDepot`-backed callers (e.g., `scope_resources.ex`, `student_progress_rows/2`) — no new failure mode is introduced, and no new defensive fallback is added beyond what those existing callers already rely on.
- If a page's resolved parent container is absent from `decorated_numbering_map/1` for a reason other than suppression (e.g., a data-integrity edge case where the container isn't part of the current hierarchy), the row is treated as "no container label," which is a safe, non-crashing degradation identical to today's existing "no parent container" case in `name_with_container_label/3`.
- If the migration's batch loop is interrupted (deploy timeout, node restart, transient DB error on one batch), the safe recovery is to re-run it from the start: it is idempotent (re-nulling an already-nil `previous_next_index` is a no-op) and keyset pagination by `id` guarantees termination, so a re-run simply re-scans already-completed pages quickly (no matching work left) and resumes real work at the first not-yet-reached page.

## 11. Observability
- No new telemetry events are introduced; standard AppSignal/Phoenix instrumentation already covers the affected controllers and LiveViews (per `docs/OPERATIONS.md`).
- The migration should print/log the count of rows updated (a simple `IO.puts` or migration-standard result inspection of the `UPDATE`'s affected-row count) so a deploy can confirm it touched the expected, small set of sections.

## 12. Security & Privacy
- No new authorization surface: every affected view already scopes its query to the current section, and this change only affects which numbering value is shown, not what data or which sections a given user can reach.
- No new data exposure: `decorated_numbering_map/1` derives from the same section hierarchy data already accessible to each existing call site's caller.

## 15. Risks & Mitigations
- Risk: replacing narrow per-page SQL lookups with a full decorated hierarchy build (Group A/B) adds latency for very large courses. Mitigation: `decorated_numbering_map/1` sources its data through the `SectionResourceDepot` cache (Section 4.1, 9) rather than a fresh query, and reuses the same decoration mechanism (`DisplayNumbering.decorate_hierarchy/2`) already proven at scale by other Depot-backed consumers; manual/automated latency verification is still planned during implementation on a representative large course.
- Risk: the `previous_next_index` migration's predicate is miscalibrated (too broad, forcing unnecessary rebuilds, or too narrow, missing affected sections). Mitigation: the predicate directly mirrors the same `unnumbered_unit_ids` non-empty condition the PRD and this FDD use everywhere else; a migration test (AC-017) asserts the exact boundary.
- Risk: partial implementation across twelve independent call sites re-creates a smaller version of the original inconsistency. Mitigation: each surface is a distinct FR/AC pair in `requirements.yml`, giving explicit, individually verifiable completion tracking rather than one monolithic "ticket done" signal.
- Risk: the pattern that produced FR-014 (correct data computed upstream, silently dropped by an intermediate allowlist/filter before reaching an already-correct renderer) could recur in a location not yet found, since it does not require a raw-SQL bug at all. Mitigation: implementation should grep for other `thin_hierarchy`-style field-allowlist or field-selection utilities operating on decorated hierarchies as a final sweep before this work item is closed, rather than treating the twelve identified locations as necessarily exhaustive against this specific sub-pattern.
- Risk: the FR-010/FR-011 migration's keyset-pagination-over-`sections.id` design (Section 6) assumes the `sections` table is large enough, or its row count unknown enough, to warrant batching over a single `UPDATE`, without a confirmed production row count. Mitigation: this is treated as the safe default regardless of actual scale (a small table simply completes the batch loop in one or two iterations with no added risk), per Backfilling.md's explicit guidance not to assume scale from a lower environment; see also Section 16.

- **Migration design refined beyond the FDD's Section 6 sketch, confirmed sound by review**: the FDD described filtering each page's SELECT directly by `array_length(unnumbered_unit_ids, 1) > 0`. The implementation instead splits each page into a SELECT bounded purely by primary key (no domain predicate at all) followed by an UPDATE that applies the real predicate only within that already-bounded batch. This matters because a SELECT filtered directly by the domain predicate would need to scan an unbounded number of rows past the last processed id to fill a page if suppressed sections are rare relative to the whole table -- defeating the point of keyset pagination. The two-step design bounds every page's cost to exactly the batch size regardless of match rarity; the Phase 7 performance review explicitly verified this reasoning holds. This is a refinement of the mechanism, not a change to the migration's intent or predicate.

- **Phase 8 pattern sweep, one finding, confirmed out of scope**: performed the FDD's own explicit follow-up (Section 15's last risk) via two convergent searches -- every `Map.take/2` call site in `lib/` cross-checked against hierarchy/numbering context, and every reference to `"display_numbering"` across `lib/` to confirm every producer and consumer is accounted for. Found one previously-unaudited raw-numbering read, `Helpers.build_units_and_modules_options/1` (`lib/oli_web/live/delivery/instructor_dashboard/helpers.ex:275-295`), which reads `numbering_index`/`numbering_level` straight from `SectionResourceDepot.containers/2` with no suppression overlay. Traced its only consumer (`instructor_dashboard_live.ex`'s `:units_and_modules_options` assign) and confirmed, via a repo-wide search including `.heex` templates, that it is never actually rendered anywhere -- dead code, not a live bug. Per the PRD's scope criteria (an actually-displayed label), this is out of scope; left unfixed and documented here rather than silently dropped. If this function is ever wired to a real UI later, it will need the same `overlay_suppression_aware_numbering/2` treatment as its sibling functions in the same file. No other instance of FR-014's specific pattern (a field-allowlist silently dropping `display_numbering` from an already-decorated hierarchy) was found beyond the two callers already fixed in Phase 2.
- **`Oli.Scenarios` has no directive for `unnumbered_unit_ids`, confirmed via a pre-implementation audit before writing Phase 8's scenario test**: the framework's `section` directive (`test/support/scenarios/docs/sections.md`) has no parameter for section-level customizations like `unnumbered_unit_ids`. This isn't a blocker -- `Engine.execute/2`'s `ExecutionState` hands back a real, DB-persisted `%Oli.Delivery.Sections.Section{}` struct (via `Engine.get_section/2`), so `unnumbered_unit_ids` is applied with a plain `Sections.update_section/2` call after the scenario finishes building the section, before running any assertions. Cross-surface assertions themselves are also plain `Phoenix.LiveViewTest`/ExUnit code against the real section/project the scenario produced, not a constrained scenario-specific assertion DSL -- confirmed no existing scenario test in this repo does LiveView-based assertions, so this is a new (but unremarkable) pattern for this test.
