# MER-6118: deleted activity references

This enhancement supersedes the original tool's active-shared-only repair scope.
The tool remains system-admin-only at
`/workspaces/course_author/:project_slug/repair_tool`; no navigation entry is added.

## Analysis and repair

Analysis scans current, non-deleted, project-scoped Basic pages, including nested
activity references and every alternative branch. Adaptive pages remain excluded.
Targets are classified using only the project's working-publication mappings:

- Active: repair cross-page sharing when present.
- Deleted: create a tracked active revision under the existing resource ID.
- Unresolved: no valid project-scoped activity revision in the working publication;
  report only, preserving the reference. This includes absent, foreign, and
  wrong-type targets; it does not claim that no historical record exists anywhere.

Deletion and sharing overlap. The deleted report includes that overlap explicitly;
its counts must not be added to the shared counts as distinct activities. Reference
counts count page/activity pairs, so repeated nodes on one page count once.

For shared targets, the lowest page resource ID keeps the original activity.
Other pages receive independent active copies. Deleted originals are restored
before cloning. Unchanged keeper and single-reference pages receive no gratuitous
page revision. Sources and all participating pages use the existing authoring lock
protocol, with page and source revision/deletion state revalidated before writing.
Display limits never constrain repair planning.

Restorations commit individually and page rewrites commit individually with their
clones. A later failure can leave a valid partial repair (including restored but
still-shared targets). The result reports committed counts and remaining issues;
a retry restores only remaining deleted targets and clones only remaining sharing.

Repair modifies only unpublished authoring state. Publication, section updates,
and learner attempts are untouched. Publication and section updates must be done
separately. Clones change activity identity on non-keeper pages. This tool does not
migrate learner data or refresh existing page attempts that lack activity attempts.

## Verification without production data

Run `mix test test/oli/authoring/project_repair_test.exs test/oli_web/project_repair_route_test.exs`.
The tests construct corrupt working-publication relationships directly in the local
SQL sandbox: single and shared deleted activities, nested/hidden alternatives,
unresolved targets, lock conflicts, changed source revisions, and partial retry.
They also verify publication/section update and delivery for a restored target,
with an existing learner attempt and a fresh learner.

A production export is not a reliable fixture: export omits deleted revisions.
Use these synthetic cases for regression coverage. For manual QA on a disposable
development project, reference an activity from two Basic pages, create a tracked
revision setting `deleted: true`, then open the repair URL as a system admin.
Analysis must distinguish the deleted/shared overlap, repair must retain the
keeper's ID and create one active copy, and repeating repair must make no changes.
