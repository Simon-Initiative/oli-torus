# Persistence and Configuration Slice

## Scope

This slice owns the additive PostgreSQL model, canonical strategy normalization, draft configuration APIs, activation validation, lifecycle integrity, and dependency reconciliation described in Phases 2 and 3. It does not own delivery rendering, reward processing, or authoring presentation.

## Confirmed Current Contracts

- `Oli.Experiments` is the public domain boundary. The current create and update request structs expose one `decision_point` and a flat condition list; every in-repository caller must move to the multi-point contract in the same unit of work.
- Conditions are currently decision-point-owned and unique by `(decision_point_id, condition_code)`. Assignments are unique by `(experiment_id, decision_point_id, enrollment_id)`. Policy state is unique by `(experiment_id, decision_point_id, algorithm)`.
- Activation currently requires exactly one decision point and checks conflicts by Alternatives resource and decision-point key. Structural writes are guarded primarily by context logic rather than the future intervention and binding constraints.
- Existing persisted strategy is `upgrade_decision_point`; new writes must use `experiment_controlled`, with the former accepted only as a read/ingest alias.

## Public API Boundary

Replace the single-point request shape with an experiment graph containing:

- experiment-owned conditions with stable database identities and author-facing labels;
- a list of decision points, each with algorithm, guardrails, condition-to-option mappings, ordered interventions, and optional assessment bindings;
- explicit draft reconciliation operations for removing a mapping, intervention, assessment binding, or group dependency.

All public reads and writes accept or derive `Oli.Experiments.Scope`, enforce project/section ownership and author membership centrally, deny cross-project and cross-tenant access by default, return public structs/errors, and never expose Ecto schemas. Structured validation errors identify the decision point, mapping, intervention, or assessment binding that failed without disclosing inaccessible object details.

### Condition Identity

Each condition has two stable identifiers with distinct roles:

- `experiment_conditions.id` is the internal relational primary key used by foreign keys and joins;
- `condition_code` is the stable, readable experiment-scoped identifier used by policy-state JSON, APIs, diagnostics, and analytics evidence.

The remaining condition fields have separate responsibilities:

- `label` is the author-facing human-readable name and may change while the experiment is in draft;
- `option_id` is the stable identifier of an Alternatives Group option mapped to the condition at one decision point;
- `condition_code` is generated once from the initial label and never changes when the label changes.

The same condition can map to different `option_id` values at different decision points. For example, condition code `control`, backed by condition ID `42`, might map to option `baseline-content` at one decision point and `standard-feedback` at another.

Generate new codes inside the experiment configuration transaction while holding the experiment row lock:

1. Normalize the initial label with `Oli.Utils.Slug.slugify/1`; use `condition` when normalization is empty.
2. Use the normalized base when it is unused in the experiment.
3. On collision, append the smallest available deterministic numeric suffix: `control`, `control-2`, `control-3`, and so on.
4. Enforce `UNIQUE (experiment_id, condition_code)` in PostgreSQL as the final invariant.

All supported condition creation must occur under the experiment lock, so concurrent requests cannot select the same suffix. The database constraint remains mandatory as defense in depth and converts any unexpected race into a structured retryable conflict rather than silently changing an existing code.

Current rows retain their existing option-derived codes. The migration does not rename or merge them. When normalizing legacy conditions from multiple decision points into experiment ownership, matching codes alone do not prove shared identity; preserve row IDs and fail the migration validation if the same experiment contains conflicting rows that cannot be reconciled without an explicit mapping decision.

Both condition ID and code are immutable after creation. Draft edits may change labels or mappings, but deleting and recreating a condition creates a new identity and code. Once assignments, policy state, rewards, or evidence reference a condition, supported APIs reject deletion or identity changes.

For an atomic graph-create request, a new unsaved condition carries a request-local `client_ref`, generated by the UI or server request builder. Decision-point mappings in that same payload refer to the `client_ref`; `Oli.Experiments` validates that it is non-empty and unique only within the request, inserts the conditions, resolves each reference to its generated database ID, and persists only `condition_id` foreign keys. The response returns the created condition IDs. Updates to persisted graphs refer directly to `condition_id`. `client_ref` is never stored, emitted as analytics identity, or reused across requests.

## Persistence and Indexes

Use dependency-ordered generated Ecto migrations with explicit `up/0` and `down/0`:

1. Normalize `experiment_conditions` to experiment ownership while preserving every existing row ID and code; replace decision-point code uniqueness with unique `(experiment_id, condition_code)`.
2. Add `experiment_decision_point_conditions` with non-cascading foreign keys and unique pairs `(decision_point_id, condition_id)` and `(decision_point_id, option_id)`.
3. Add `experiment_interventions`, unique `(decision_point_id, page_resource_id, content_element_id)` and indexed `(page_resource_id, content_element_id)`.
4. Add `experiment_assessment_bindings`, unique by intervention; enforce assessment reuse within a current experiment under the experiment lock.
5. Extend assignments, accepted-reward identity, and policy configuration only after their referenced tables exist.

Legacy rows remain readable and nullable where intervention identity cannot be inferred. New changesets require complete intervention-scoped state. Every foreign key added by this work uses `on_delete: :nothing`; draft APIs reconcile dependencies explicitly.

## Transaction Ownership

- Draft graph save and activation are owned by `Oli.Experiments` and run under an experiment row lock.
- Activation locks referenced group resources in sorted resource-ID order before checking current-binding exclusivity.
- Configuration display ordering comes from current hierarchy/content traversal; stable IDs are tie-breakers and persistence identity, not placement order.
- Completed and archived history is immutable. A completed or archived prior binding does not block a later independent draft binding.

## Migration and Rollback Order

Forward order is condition ownership normalization, mapping tables, interventions/bindings, assignment/reward extensions, then constraints and indexes. Preserve each legacy condition ID and code; never infer that matching codes represent one shared condition without explicit compatible mappings. Copy the old decision-point relationship, option ID, weight, and position into `experiment_decision_point_conditions`, then make the condition row experiment-owned and install experiment-scoped code uniqueness. Policy state remains keyed by `condition_code`. Rollback removes dependent constraints and columns first, restores the prior decision-point-scoped code constraint and mapping fields, then removes the new tables.

## Gate Dependencies

This slice begins after Gate A. Assignment, reward, UI, and interop slices consume its stable IDs and public graph contract; they must not bypass this context.

## Decision Log

### 2026-08-11 - Retain readable condition codes

- Change: Retain immutable `condition_code`, generate it from the initial label under the experiment lock, resolve collisions with deterministic numeric suffixes, and enforce experiment-scoped database uniqueness.
- Reason: Removing the established code contract would broaden this work across policy, delivery, reward, analytics, and tests; readable stable codes remain useful for diagnostics and evidence.
- Evidence: Current native experiment policy state, assignment responses, and analytics already use option-derived condition codes.
- Impact: New codes are readable and guaranteed unique within an experiment without label-collision races; database IDs remain the relational identity, and existing codes are preserved without automatic renaming or merging.
