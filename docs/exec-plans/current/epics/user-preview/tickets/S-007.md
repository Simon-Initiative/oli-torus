# S-007: Reuse delivery layouts and views for authoring page preview

- **Status:** Approved and pending creation
- **Qualification:** Qualified. Targeted code inspection confirms that author preview duplicates delivery presentation and that the current learner layout depends on learner/LiveView state. Shared presentation can accept explicit preview context/assigns while preserving the author resolver and preview activity bridge. Both basic and advanced paths need integration.
- **Lane:** B, first.
- **Ticket:** pending.

## Description

Make author Page Preview reuse the actual delivery page layouts and views so delivery UX changes appear in preview through the same implementation.

- **Requirements:** [MER-6158](https://eliterate.atlassian.net/browse/MER-6158), R-004, R-008. Full requirements are in the epic ticket.
- **Scope:**
  - Allow shared presentation to accept explicit preview context and assigns without a database-backed learner account. Keep real-author/project authorization separate.
  - Integrate both basic and advanced author preview, preserving working content, activity interactions, adaptive sequence behavior, and selection errors.
  - Provide the secondary Page preview action, sticky Page Preview banner, and editor return/focus behavior. Exclude course navigation, outline, DOT, and instructor notes.
  - Remove duplicated preview presentation while retaining thin adapters for runtime differences. Preview must not provision learner accounts, sections, enrollments, persisted attempts, or progress merely to render.
- **Technical approach:** Adapt or extract the existing delivery presentation components while leaving learner loading and lifecycle in their current callers. Keep AuthoringResolver and the nonpersistent preview activity bridge, and integrate basic and advanced preview through the shared presentation boundary. Proposed implementation details are provisional; required behavior and binding constraints remain mandatory.
- **Acceptance criteria:**
  - **Positive:**
    - P1 — Page preview opens the current working page, including unpublished changes.
    - P2 — Page Preview and a usable exit remain visible while scrolling; exit returns to the originating editor and focuses its launch control.
    - P3 — The entry, banner, and exit support keyboard operation, narrow widths, and increased zoom.
    - P4 — Basic and advanced preview retain their existing activity/runtime behavior and selection failures remain visible.
    - P5 — Basic and advanced author preview use the applicable shared delivery layouts/views/components. Changes to shared page presentation are reflected in preview without a matching edit to a separate preview implementation.
    - P6 — Shared presentation accepts explicit preview context/assigns and renders for an authorized author without a database-backed learner user; normal delivery continues to render with its existing learner state.
  - **Negative:**
    - N1 — Single-page preview has no previous/next, course back, course outline, DOT, or instructor notes.
    - N2 — Preview cannot read an unauthorized project's content, change its publication, or silently fall back to student delivery.
    - N3 — Removing navigation does not remove supported evaluation, reset, hints, or adaptive sequence selection.
    - N4 — Preview creates no learner account, hidden learner, delivery section, enrollment, persisted learner attempt, or progress solely to render shared delivery UI. Author/project authorization remains enforced.
    - N5 — No independently maintained copy of delivery page presentation remains in the affected preview paths. Thin preview adapters preserve runtime differences and leave unrelated template consumers intact.
- **Prerequisites:** None.
- **Size:** XL.
- **Sub-tasks (in order; both required for Story acceptance):**
  - **S-007a — Shared delivery presentation boundary.** Adapt/extract the affected delivery layouts, views, and page components to accept caller-supplied display context and capabilities. Preserve normal learner delivery, including account-bound behavior outside the presentation boundary. Verify rendering with delivery state and learner-free preview assigns (P5/P6, N4/N5).
  - **S-007b — Integrate basic and advanced author preview.** Use the shared presentation from both author-preview paths, remove duplicated preview UI, and implement the entry/banner/exit/focus contract. Preserve author authorization, working content, preview activity bridge, selection errors, and adaptive sequence/runtime semantics. Verify all Story criteria, including no new learner records and normal delivery regression coverage.
- **Feature flags:** None.

## Local analysis

- **Requirements analysis:**
  - [R-004](docs/exec-plans/current/epics/user-preview/epic.md#r-004-preview-a-working-authoring-page): Reuse delivery presentation for basic and advanced author preview through caller-supplied context/assigns. Show working content, a secondary Page preview action, sticky Page Preview banner, and exit/focus return. Exclude previous/next, course back, outline, DOT, and instructor notes.
  - [R-008](docs/exec-plans/current/epics/user-preview/epic.md#r-008-keep-preview-controls-accessible-and-authorized): Preserve author/project authorization, keyboard access, visible focus, and narrow-width/zoom behavior. Q7 supplies labels and sentence casing.
- **Scope analysis:**
  - Adapt page-delivery layouts, views, and shared presentation components to receive explicit display context and capability assigns from delivery or author preview callers.
  - Route basic and advanced author page preview through that shared presentation. Replace duplicated preview page UI with shared rendering; retain only thin preview adapters where needed.
  - Update the editor entry, sticky banner, and exit/focus behavior. Preserve working-draft resolution, selection errors, author-preview activity interactions, and adaptive sequence/runtime behavior.
  - Keep learner data loading, enrollment, authorization, and attempt lifecycle outside the shared presentation boundary. Preview still authorizes the real author; it requires no learner account, hidden learner, delivery-section provisioning, enrollment, or persisted learner attempt.
  - S-008/S-009 own limitation indicators; S-010 owns bank-question preview. Preserve other consumers of shared templates and avoid a broader container, account-menu, or delivery-lifecycle redesign.
- **Sources and design:** [Design Handoff](https://docs.google.com/document/d/1XrwiN86AETdRxxyoGanQE2pAvl484RHPM6w0prWKk6c/edit); [Page preview frame](https://www.figma.com/design/S8qAFhjjlnRyTHCg2Dyb8p/User-Preview-Overhaul?node-id=484-13987). Use the approved written and static-design evidence; the inaccessible Make prototype supplies no requirements. Figma-backed implementation follows the repository UI workflow.
- **Analysis:**
  - **Existing behavior:** `ResourceController.preview/2` resolves through `AuthoringResolver`, uses the working publication for bank selection, and renders author-preview activity content. `editor_live.ex` and `PageEditor.tsx` already launch a named window. Normal lesson presentation is spread across `lib/oli_web/components/layouts/student_delivery_lesson.html.heex`, `lib/oli_web/components/layouts/page.html.heex`, `lib/oli_web/components/delivery/layouts.ex`, `Student.Utils.page_header/1` and `references/1`, and `LessonLive` render branches/private `page_content_with_sidebar_layout/1`.
  - **Remaining gap:** `lib/oli_web/templates/resource/page_preview.html.heex` separately maintains page layout, spacing, banner, references, and navigation. The learner layout depends on socket, section, page context, token, and lifecycle assigns; directly mounting `LessonLive` would require a learner and create attempts. Shared presentation must be callable independently of that lifecycle. Account/header components also need explicit display inputs or capability-based omission of account-only actions. `resource/advanced_page_preview.html.heex` and `page_delivery/advanced_delivery.html.eex` duplicate script/React delivery mounting. Styling the existing preview templates alone would leave the divergence in place.
  - **Verification and uncertainty:** Targeted subagent and coordinator code/test inspection only; no tests or browser checks run. Existing resource-controller/editor tests cover working preview links, selection errors, and adaptive `previewSequenceId`. Development must settle the smallest shared component/assign boundary, verify author-only rendering with no learner identity, preserve normal learner delivery, and exercise basic/advanced preview, zoom, scrolling, and cross-window focus. Other container-preview consumers do not justify a container redesign.
- **Technical analysis:**
  - **Binding constraints:** Share delivery presentation rather than copy its markup/styles into another preview view. Accept preview context/assigns without a database-backed learner; keep actual author/project authorization intact. Preserve normal learner delivery and the existing nonpersistent author-preview activity behavior. Preview-only navigation restrictions and banners remain explicit.
  - **Shared presentation:** Adapt or extract the existing delivery page layout, header, content, and reference components so callers supply page/course display data, relevant capabilities, and content. Delivery callers supply their existing state; preview callers supply working-page data and preview assigns. Keep learner-only data loading and event handling in their existing callers. Use the existing component attribute patterns or a small presentation context as needed; do not build a generic rendering framework or fabricate learner IDs to satisfy account-bound helpers.
  - **Preview integration:** Keep `ResourceController`, `AuthoringResolver`, and the preview activity bridge. Render basic preview through the shared page presentation, passing explicit restrictions for navigation, notes, and DOT. Remove duplicated presentation from the basic preview template or turn it into a thin adapter. Share the applicable advanced delivery wrapper/mounting presentation while retaining preview-specific `app_params`, `previewMode`, `previewSequenceId`, and runtime behavior. Preserve Instructor View and other existing consumers of the advanced preview template.
  - **Entry and exit:** Keep the named-window entry and originating editor. Use a secondary Page preview action, a shared sticky Page Preview banner, a stable launch focus target, and an exit that restores the opener or uses a safe authoring fallback. Any preview-only wrapper supplies context/bridge behavior without maintaining another copy of delivery UI.
  - **Verification:** Update tests that currently require preview previous/next links. Add focused coverage that renders both delivery and preview through the shared presentation, renders preview with an authorized author and no learner account, and verifies no learner account/enrollment/attempt/progress records are created. Preserve working-content, selection-error, supported activity, adaptive sequence, and ordinary delivery regression coverage. Verify focus, reflow, and sticky behavior in the browser.
- **Prerequisite handoffs:** None. S-008 and S-009 can modify their rendering paths independently; placing them later in Lane B reduces shared preview verification work and is a scheduling choice.
- **Sizing analysis:** XL; shared delivery presentation must be separated from learner lifecycle/account assumptions, then integrated into basic and advanced preview with regression and cross-window focus coverage.
