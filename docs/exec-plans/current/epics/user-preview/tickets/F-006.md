## Description

**Figma frames / prototype:** [Figma](https://www.figma.com/design/S8qAFhjjlnRyTHCg2Dyb8p/User-Preview-Overhaul?node-id=484-13207&t=5eBSflw0qUqbFcPl-1)

### User Need

As an author, I want to know when content is unavailable or behaves differently in page preview, so that I can distinguish preview limitations from problems with my content.

### Acceptance Criteria

**Successful behavior**

- When content has a known preview limitation, display an information icon next to the affected content or its placeholder.
- The icon opens a tooltip explaining the specific limitation in plain language.
- Distinguish between content that is unavailable, content with limited functionality, and content that uses sample data.
- If content cannot be displayed, retain a labeled placeholder so authors can identify what belongs in that location.
- Use consistent messaging for the following limitations:

| **Content / activity** | **Preview messaging** |
| --- | --- |
| **LTI external tool** | “You cannot interact with this tool in page preview.” |
| **File upload** | “File uploads are not available in page preview.” |
| **Directed discussion** | “Posting to discussions is not available in page preview.” |
| **Logic Lab** | “You can open this lab in page preview, but scores are not recorded.” |
| **Activity reports** | “This is sample data. Actual activity reports are not available in page preview.” |
| **OLI embedded activities** | If a preview session cannot be created: “Preview is not available for this activity.” |
| **Surveys** | “After submitting this survey in page preview, you cannot reset it here.” |
| **Alternatives** | “Page preview shows all alternatives. Students receive content according to the configured selection rules.” |
| **Page collaborative spaces** | Display a placeholder: “Collaborative spaces are not available in page preview.” |

**Exceptions and safeguards**

- Show limitation indicators only for affected content. Ordinary scored activities that work in preview must not be labeled as unsupported.
- Preview limitations must not prevent authors from reviewing other content on the page.

### Accessibility Requirements

- **Keyboard:** Use a keyboard-focusable button for each information icon. Open its tooltip on keyboard focus and pointer hover, and allow dismissal with Escape without moving focus.
- **Semantics and labels:** Give each trigger a descriptive accessible name, such as **Preview limitation: File upload**, and associate the tooltip text using aria-describedby. Hide decorative icons from assistive technology.
- **Tooltip behavior:** Keep the tooltip visible while the trigger or tooltip is hovered, or while the trigger has focus, unless dismissed. Tooltips must not contain interactive controls; use an appropriate popover if actions are needed.
- **Content and visibility:** Keep unavailable-content placeholders in the normal reading order. Ensure messages remain readable at increased zoom and do not rely on color alone to communicate limitations.

### Constraints

- These requirements apply to authoring page preview at /authoring/project/:project/preview/:page, which renders the working draft.
- Normal activities evaluate in the browser through /project/test/evaluate; answers, scores, and hints are not persisted.
- Activity-bank selections use the working publication.
- Preserve existing preview functionality for supported activities. This work communicates limitations; it does not add support for unavailable functionality.

## Technical Guidance

### Size and feasibility

- **Size:** L (6–10 focused engineering days).
- **Single-engineer feasibility:** Good individual assignment. Most underlying behavior exists. Effort comes from nine content types and accessible information triggers in React and server-rendered previews.
- **Estimate basis:** An engineer familiar with Torus; includes implementation and verification, excludes dependency/review waiting time. This is a planning estimate, not a delivery commitment. Story effort includes any sub-tasks; do not add the Story and sub-task estimates together.

### Suggested approach

Add the exact messages above only in author Page Preview. Use a small reusable information trigger across the affected server-rendered and React content. Keep supported interactions working; this Story communicates limitations rather than adding unavailable functionality.

The trigger must be named, keyboard reachable, associated with its tooltip, visible on focus/hover, and dismissible with Escape without moving focus. Keep placeholders in reading order and tooltip content noninteractive. `components/common/Tooltip.tsx` is currently a Bootstrap/title wrapper; `lib/oli_web/components/tooltip.ex` uses a LiveView hook. Verify actual initialization in controller-rendered preview before choosing what to reuse.

### Existing behavior by content type

| Type | Relevant code and change |
| --- | --- |
| LTI tool | `LTIExternalToolDelivery.tsx` already suppresses interaction in `author_preview`; replace its warning copy/presentation. |
| File upload | `FileUploadDelivery.tsx` currently calls section/attempt upload APIs; add the author-preview message without adding upload support. |
| Discussion | `DirectedDiscussionDelivery.tsx` uses section-backed APIs; add the no-posting message. |
| Collaboration | Supply a labeled placeholder from page collaboration settings only when a space is configured. |
| Embedded activity | `OliEmbeddedDelivery.tsx` already requests a preview session and sets `previewError`; show the message on failure only, retaining loading and successful interaction. |
| Logic Lab | `LogicLabDelivery.tsx` already opens the lab without recording preview scores; add the explanation. |
| Reports | `lib/oli/rendering/report/html.ex` already uses a fixed sample dataset for author preview; label it as sample data. |
| Surveys | `PageEditor.render_page_html/4` leaves `resettable_surveys` empty; `SurveyControls.tsx` omits Reset when `canReset` is false. Add the explanation without changing that behavior. |
| Alternatives | `lib/oli/rendering/alternatives/html.ex` already exposes all options through tabs or a preference selector. Replace the notice presentation with the exact generic handoff message; preserve those controls and student selection rules. |

### Checks

Exercise all nine types in actual author Page Preview, including embedded success/failure, configured/unconfigured collaboration, both alternatives strategies, and survey state after submission. Include a working scored activity to verify normal evaluation/hints/reset and continued review of the rest of the page. Do not label supported activities as unavailable or change ordinary delivery/instructor-preview behavior.

Reuse `test/oli/rendering/survey/html_test.exs` and `test/oli/rendering/alternatives/html_test.exs`; update assertions for the replaced alternatives notice. If runtime behavior contradicts a required message, resolve that mismatch rather than disabling working functionality to make the message true. Button labels follow the handoff's Title Case guidance. Exact component packaging is an engineering choice.
