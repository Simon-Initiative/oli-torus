# S-012: Prepare a project review section and published-course launch

- **Status:** Created and verified
- **Qualification:** Qualified. Targeted code inspection supports initial section creation, mandatory Publish-triggered updates through existing Oban infrastructure, launch readiness checks using publication/job state, and explicit failed-preview recreation. Structural refresh, ordering, and pending/failed-state handling need explicit implementation; existing identity/progress behavior is reused.
- **Lane:** D, first; followed by S-015, S-016, S-014, and S-013; S-016 → S-014 is scheduling only.
- **Ticket:** [MER-6199](https://eliterate.atlassian.net/browse/MER-6199)

- **Sub-task tickets:** S-012a = [MER-6200](https://eliterate.atlassian.net/browse/MER-6200); S-012b = [MER-6201](https://eliterate.atlassian.net/browse/MER-6201); S-012c = [MER-6202](https://eliterate.atlassian.net/browse/MER-6202)
## Description

Maintain one published-course preview section per project, keep it updated on Publish, and launch only when it is ready.

- **Requirements:** [MER-6158](https://eliterate.atlassian.net/browse/MER-6158), R-007, R-008, R-011. Full requirements are in the epic ticket.
- **Scope:**
  - Create the marked preview section from the latest publication on first launch if absent. Every subsequent successful Publish queues its full structural update, independently of optional pushes to normal sections.
  - Before launch, report updating or failed state rather than opening stale or partial content. Launch itself does not rebuild or refresh the section.
  - Offer Reset Preview only for failed project previews to authorized project authors and admins. Create a fresh latest-publication section and replace the association; fresh progress follows naturally from the new section.
  - Preserve normal-update progress, including older revisions retained by active graded attempts. Identify retired preview sections for later queries; cleanup is outside scope.
- **Technical approach:** Reuse existing section creation, publication updates, Oban jobs, and lifecycle mechanisms. Add the minimal project association, transactional Publish scheduling, durable readiness checks, and ordering/concurrency safeguards. Provide an authorized Learn/new-tab session handoff for S-015 and S-014 without return tracking. Proposed implementation details are provisional; required behavior and binding constraints remain mandatory.
- **Acceptance criteria:**
  - **Positive:**
    - **AC1** Authorized first launch creates or resolves the project's review section; repeated and concurrent launches reuse it.
    - **AC2** Every successful Publish schedules an update for an existing project review section, even when normal-section auto-push is off. Completion applies the latest publication and its hierarchy additions, removals, and changed pages. Launch checks completion/currentness without performing the update itself.
    - **AC3** Review and Publish open the same authorized project launch in a new tab, with Learn entry and the enrollment/session foundations used by S-015’s preview identity integration. The launch is announced as opening a new tab. Exit preview closes that tab; no origin-specific return URL or close-failure fallback is required. Existing product/template behavior remains compatible.
    - **AC4** After a Publish-driven update completes, the section uses the latest publication while existing in-progress graded attempts retain older revisions where the normal lifecycle does so. Attempts and progress are preserved without automatic reset.
    - **AC9** A failed project Full Course Preview exposes Reset Preview to authorized regular project authors and admins. It recreates the managed section from the latest publication, updates the project association, and provides a ready preview whose initial state comes from normal section creation; the effect on shared preview state is explained.
    - **AC11** A direct database query can identify every dedicated project preview section created or replaced by this feature, including retired sections. Ordinary delivery sections and reusable product/templates are excluded from that classification. No cleanup process is introduced.
  - **Negative:**
    - **AC5** Unpublished or unauthorized projects cannot launch or allocate another project's review section.
    - **AC6** Pending, retrying, failed, stale, or incomplete latest-publication updates do not open preview; the launch response identifies updating or failed state. Draft revisions and partial updates are excluded, and launch does not rebuild the section.
    - **AC7** Concurrent launches create no duplicate review sections; initial-creation/Publish races cannot lose an update, older jobs cannot regress the section, and rolled-back publishes enqueue no update. Normal launches/updates preserve the selected preview identity and its progress; failed-state Reset Preview recreates the shared section, while Reset Preview User in S-015 separately replaces one author’s preview identity.
    - **AC8** Existing product/template preview behavior remains compatible.
    - **AC10** Reset is denied for unauthorized authors, other projects, ordinary delivery sections, product/template previews, and non-failed preview states. Concurrent resets and stale update jobs cannot corrupt or replace the new association; retired preview sessions cannot bypass association validity even for admins, and reset failure preserves a recoverable failed association without exposing a partial replacement or deleting actual user/author accounts.
- **Prerequisites:** None.
- **Size:** XL.
- **Sub-tasks (in order; all required for Story acceptance):**
  - **S-012a — Review-section association and Publish-driven updates.** Implement initial create/reuse with a durable preview-purpose marker, transactional publish scheduling, and coherent structural updates using existing queue infrastructure. Verify duplicate/concurrent creation, first-creation/Publish races, optional-push independence, obsolete jobs, retries, draft exclusion, and rollback on update failure.
  - **S-012b — Authorized launch, readiness, and session contract.** Add project authorization, current/complete/pending/failed outcomes, Learn entry, and the new-tab preview context contract. No dynamic return destination or fallback redirect is needed. Launch performs readiness checks but no refresh. Verify the agreed identity handoff, denied/unpublished access, initial creation failure, queued/retrying/failed updates, retained progress, and older active-attempt revisions under Q10.
  - **S-012c — Failed-state Reset Preview recovery.** Add the project-scoped, author/admin-authorized reset operation and accessible failed-state action. Recreate from the latest publication, replace the managed association, explain fresh shared progress, and retire the old section through existing mechanisms while retaining its preview marker. Preserve actual accounts and require fresh launch context for the replacement. Verify regular author/admin access, denied and non-failed cases, no impact on other section types or real accounts, concurrent reset/Publish/update races, obsolete jobs, retired preview sessions/admin bypass, and reset failure (AC9/AC10).
- **Feature flags:** None. S-014 supplies the first user-facing project entry after this foundation and S-015’s identity integration are complete.

## Local analysis

- **Requirements analysis:** [R-007](docs/exec-plans/current/epics/user-preview/epic.md#r-007-preview-the-latest-published-course) requires one review section per project, initial creation from the latest publication, automatic updates on every subsequent successful Publish, launch readiness checks, Learn entry, and draft exclusion. [R-008](docs/exec-plans/current/epics/user-preview/epic.md#r-008-keep-preview-controls-accessible-and-authorized) requires project authorization and preservation of normal author/learner authentication. Full Course Preview opens in a new tab; Exit preview closes that tab, with no tracked origin, return URL, or fallback redirect. Q2 keeps the preview student-only. Q3 preserves progress during normal use with no automatic reset; S-015 owns the author-linked preview-user policy and explicit account-level reset; explicit failed-state Reset Preview creates a new section with its normal initial state; [R-011](docs/exec-plans/current/epics/user-preview/epic.md#r-011-identify-preview-users-and-sections) requires durable preview-section identification, including superseded sections; Q10 permits older revisions retained by active graded attempts after the section publication advances.
- **Scope analysis:** Add the minimal durable project-to-review-section association, initial create/reuse, mandatory Publish-driven update scheduling, full structural refresh, an authorized new-tab launch/readiness/session contract, persistent preview-section identification, and failed-state Reset Preview recovery. Launch checks readiness but does not refresh an existing section. Expose pending/failed outcomes and a failed-state Reset Preview action through the shared launch response; S-014/S-013 own their visible entry actions and shell. Reuse existing identity, enrollment, progress, and update-job mechanisms.
- **Sources and design:** [Design Handoff](https://docs.google.com/document/d/1XrwiN86AETdRxxyoGanQE2pAvl484RHPM6w0prWKk6c/edit); [existing template preview](https://www.figma.com/design/S8qAFhjjlnRyTHCg2Dyb8p/User-Preview-Overhaul?node-id=553-14997); [Learn](https://www.figma.com/design/S8qAFhjjlnRyTHCg2Dyb8p/User-Preview-Overhaul?node-id=563-30474). Designs are the approved static evidence; the inaccessible Make prototype is excluded.
- **Analysis:**
  - **Existing behavior:** `Oli.Delivery.TemplatePreview.prepare_launch/3` in `lib/oli/delivery/template_preview.ex` accepts active blueprint sections. It authorizes the author, ensures student enrollment for a current user, and creates/reuses the section's hidden instructor when needed. `ProductsController.preview_launch/2` in `lib/oli_web/controllers/products_controller.ex` sets a section-scoped session, logs in the hidden user where applicable, and redirects to the section root. `preview_exit/2` clears that session, logs out only a hidden user, and preserves the author session. `test/oli/delivery/template_preview_test.exs` and `test/oli_web/controllers/products_controller_test.exs` cover identity reuse, enrollment reuse, unauthorized access, and exit cleanup.
  - **Existing behavior:** `Blueprint.create_blueprint/5` in `lib/oli/delivery/sections/blueprint.ex` creates section resources from a latest publication. Section publication-update functions already handle projection, tool configuration, and caches. They need careful selection: `Oli.Delivery.Sections.Updates.do_update/4` in `lib/oli/delivery/sections/updates.ex` treats a blueprint's major publication update as a minor update. The ordinary blueprint update cannot be assumed to reproduce the latest course hierarchy.
  - **Publish and readiness foundations:** `Publishing.publish_project/3` in `lib/oli/publishing.ex` is shared by publishing entry points. Its optional `push_publication_update_to_sections/4` is invoked separately by Publish UI and cannot alone guarantee preview updates. `Oli.Delivery.Updates.Worker` in `lib/oli/delivery/updates/worker.ex` uses the existing Oban updates queue and retries. `Sections.get_current_publication/2`, `check_for_available_publication_updates/1`, and `check_for_updates_in_progress/1` provide comparison/job foundations; the last helper omits retryable and terminal failure states. Existing progress broadcasts are transient, so readiness must use durable publication/job state.
  - **Recovery foundations:** Existing section creation and `Sections.soft_delete_section/1` support fresh replacement and retirement through the project association. A new section naturally has fresh attempts/progress; no separate data-clearing operation is needed. `get_section_by_slug/1` and admin enrollment bypasses do not themselves reject retired preview contexts, so preview-specific session/association validity must prevent old sessions from continuing against the retired section. Reuse existing project access checks for both regular authors and admins.
  - **Remaining gap:** The project schema in `lib/oli/authoring/course/project.ex` has no dedicated review-section association. Existing launch requires a product/template and uses that flow’s product-return behavior; project Full Course Preview needs a distinct authorized new-tab launch. The project flow must create the section initially, schedule its updates on Publish, apply structural additions/removals, and supply a readiness-checked new-tab launch/context contract.
  - **Verification and uncertainty:** Qualification used code inspection and existing test inspection; no tests or browser flows were executed. The minimal association schema, compatible section representation, and transaction boundaries need child design. Existing attempt revision behavior is retained under Q10: `PageLifecycle.Graded.visit/1` in `lib/oli/delivery/attempts/page_lifecycle/graded.ex` returns `:revised` for an active batch-scored attempt after republishing, and `PageContext.create_for_visit/4` in `lib/oli/delivery/page/page_context.ex` then explicitly loads the revision pinned to that attempt for display. `test/oli_web/controllers/page_delivery_controller_test.exs` also covers an active attempt surviving a graded-to-ungraded publication change. The review section advances through Publish-triggered jobs; launch requires the latest publication to be applied, while resumed attempts follow existing revision behavior. Normal updates require no attempt reset or revision migration. Explicit Reset Preview creates a fresh section; its initial state follows naturally from section creation.
- **Technical analysis:**
  - **Binding constraints:** Publish drives updates to an existing review section independently of optional pushes to other sections. Launch verifies the section is current and complete, reports pending/failed outcomes, and performs no refresh itself. Preserve project authorization, structural publication changes, Q3/Q10 identity/progress behavior during normal use, and existing product/template preview compatibility. Reset Preview is an explicit recovery exception, available only for the project’s failed Full Course Preview section to authorized project authors and admins.
  - **Initial creation:** Authorize the project author and reject never-published projects before allocation. Create the dedicated section from the latest publication if absent; enforce a durable single-section association and serialize concurrent first launches. Coordinate initial creation with publishing so a concurrent publication is not missed.
  - **Preview-section identification:** Persist an explicit preview-purpose marker on dedicated project review sections at creation, including replacements created by Reset Preview. Keep that marker when an old section is retired so a database query can find current and superseded preview sections. Do not mark ordinary delivery sections or reusable product/template sections merely because someone previews them. Marker field/schema details remain provisional; cleanup, deletion jobs, retention policy, and cleanup administration are outside scope.
  - **Publish scheduling:** Schedule the review-section update from the shared successful publishing operation, transactionally with publication so rolled-back publishes leave no update job. Reuse existing Oban infrastructure/retries. The dedicated preview update is mandatory even when ordinary-section auto-push is off; prevent optional pushes from creating competing outdated updates to it.
  - **Update execution:** Reuse compatible resource updates, post-processing, external-tool initialization, and cache invalidation. Apply a complete publication/hierarchy update atomically and prevent older jobs from moving the section backward. The section representation/update strategy must handle structural changes rather than inherit blueprint minor-only behavior. Use existing retry/error mechanisms; periodic synchronization is outside scope.
  - **Launch readiness:** Compare the section's applied publication with the latest project publication and inspect the relevant durable update state, including retries/failure. Launch only after the latest update is complete; otherwise return an updating or failed outcome without opening stale/partial content. Reuse/adapt existing comparison/job helpers before introducing new status storage; live broadcasts alone are insufficient. Initial creation failure also prevents launch.
  - **Failed-state recovery:** Show a keyboard-accessible Reset Preview button with the failed project-preview response, for regular project authors as well as admins. Use a state-changing request with existing authentication/CSRF protection. Recheck project access, failed state, and the managed review-section association on the server; do not accept an arbitrary section target. Create a fresh section from the latest published publication. Its attempts/progress start fresh through normal section creation; no explicit clearing or deletion of attempts/progress is required. Establish the normal launch identity/enrollment as needed, atomically switch the project association only after the replacement is complete, and retire the old section through existing lifecycle mechanisms. Coordinate reset with Publish, update jobs, and concurrent reset requests so obsolete work cannot modify or replace the new section. Reuse existing section creation/lifecycle mechanisms, preserve actual author/user accounts, and keep ordinary delivery and product/template previews outside this operation. Explain that the shared preview restarts with fresh progress and other open previews may need to be reopened. Reject retired project-preview session/association targets, including admin bypass paths, without changing normal template sessions. A reset failure leaves the previous failed association available for retry and exposes no partial replacement.
  - **Session and progress:** Reuse compatible enrollment/session foundations while preserving existing product/template behavior. S-015 owns the distinct project Full Course Preview identity resolver and session integration; provide the launch/readiness and validated context it consumes. Supply Learn entry for a preview tab opened from Review or Publish. No origin-specific return destination is stored or propagated; Exit preview closes the tab and assumes success, with no fallback redirect. Preserve attempts and progress, including retained older active-attempt revisions during normal use; add no automatic progress reset, per-author section allocation, or retention mechanism. The separate Reset Preview User operation belongs to S-015. S-014 supplies the first complete user-facing launch/exit.
- **Prerequisite handoffs:** None. Exit handoff: the project review-section association, Publish-triggered updater, authorized readiness-checked launch, new-tab preview/session contract, and failed-state Reset Preview recovery callable by S-014 and S-013.
- **Sizing analysis:** XL; durable association, Publish integration, coherent structural updates, job ordering, readiness handling, and bounded failed-state recreation are the material work. Compatible enrollment/session foundations are reused; Exit preview simply closes the project preview tab.
