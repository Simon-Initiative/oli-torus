# S-013: Add a publication-aware Full Course Preview card to Review

- **Status:** Approved and pending creation
- **Qualification:** Qualified. Code inspection establishes the Review-card gap; Q10 defines the displayed version as the section publication. This Story follows S-014 so its launch uses a complete Full Course Preview shell and exit.
- **Lane:** D, fifth; follows S-014, with S-012 also supplying the project launch operation.
- **Ticket:** pending.

## Description

Replace Review’s working-content preview entry with a publication-aware Full Course Preview card.

- **Requirements:** [MER-6158](https://eliterate.atlassian.net/browse/MER-6158), R-007, R-008. Full requirements are in the epic ticket.
- **Scope:**
  - Never published: explain that publication is required and offer Go to Publish.
  - Published without draft changes: show the published version and Open full course preview.
  - Published with draft changes: also show the excluded-change count and Go to Publish.
  - Use the same readiness checks, failed-state Reset Preview, and new-tab shell as Publish. Preserve automated review, warnings, and the chart, with accessible status announcements and keyboard operation that do not steal focus.
- **Technical approach:** Reuse Publish’s version/diff logic and the existing Review state machinery. Connect the card to the shared project launch operation and S-014’s completed shell, rather than creating another launch or synchronization mechanism. Proposed implementation details are provisional; required behavior and binding constraints remain mandatory.
- **Acceptance criteria:**
  - **Positive:**
    - **AC1** A never-published project explains the prerequisite and offers Go to Publish.
    - **AC2** A published project without draft changes names the published version, explains that published content is used, and offers Open full course preview.
    - **AC3** Draft changes add the excluded-change count and secondary Go to Publish while preserving the primary preview action.
    - **AC4** Preview opens Learn in the section using the same latest prepared publication as Publish, in a new tab with S-014's banner and tab-closing exit; retained attempts follow Q10 during normal use; explicit failed-state Reset Preview recreates the section with fresh progress.
    - **AC5** Card name, readable status, keyboard operation, focus, and dynamic announcements satisfy R-008; existing automated review, warnings, and chart remain usable.
  - **Negative:**
    - **AC6** Never-published projects cannot launch a course preview.
    - **AC7** Draft revisions are not selected by the card or launch; stale client state cannot bypass S-012’s readiness check. Pending/failed updates are reported rather than opened, without a launch-time refresh. A failed project-preview response exposes S-012’s Reset Preview action to authorized project authors/admins and explains its shared-state effect.
    - **AC8** Project authorization remains enforced, and a card update does not steal focus or make status dependent on color alone.
- **Prerequisites:** S-012, S-014.
- **Size:** M.
- **Feature flags:** None. The card is exposed after its launch and shell prerequisites are complete.

## Local analysis

- **Requirements analysis:** [R-007](docs/exec-plans/current/epics/user-preview/epic.md#r-007-preview-the-latest-published-course) requires the three Review-card states, version/draft information, Open full course preview and Go to Publish actions, the same launch as Publish, and preservation of automated review and the chart. Under Q10, version information describes the section publication; existing in-progress graded attempts may retain older revisions. [R-008](docs/exec-plans/current/epics/user-preview/epic.md#r-008-keep-preview-controls-accessible-and-authorized) requires accessible naming, focus, readable status, project authorization, and safe navigation.
- **Scope analysis:** Replace the current generic Review preview entry with the publication-aware card and connect it to the prepared project launch. Reuse publication/diff semantics from Publish and retain all existing QA controls, warning interactions, and chart behavior. Section creation, Publish-driven updates, launch readiness, and recovery are supplied by S-012; S-015 supplies the current author preview-user identity, and S-014 supplies the banner/exit.
- **Sources and design:** [Design Handoff](https://docs.google.com/document/d/1XrwiN86AETdRxxyoGanQE2pAvl484RHPM6w0prWKk6c/edit); [never published](https://www.figma.com/design/S8qAFhjjlnRyTHCg2Dyb8p/User-Preview-Overhaul?node-id=546-53431); [published](https://www.figma.com/design/S8qAFhjjlnRyTHCg2Dyb8p/User-Preview-Overhaul?node-id=545-51964); [draft changes](https://www.figma.com/design/S8qAFhjjlnRyTHCg2Dyb8p/User-Preview-Overhaul?node-id=546-54200).
- **Analysis:**
  - **Existing behavior:** `QaLive.render/1` in `lib/oli_web/live/qa/qa_live.ex` renders Run Review and Preview Course. The latter uses `Routes.resource_path(..., :preview, project.slug)` and opens the authoring working-content preview. `mount/3`, `read_current_review/1`, and `OliWeb.Qa.State` drive warnings and review state; they do not calculate a published-course card.
  - **Existing behavior:** `PublishView.mount/3` in `lib/oli_web/live/projects/publish_view.ex` already fetches latest and working publications and calls `Publishing.diff_publications/2`. `PublicationDetails.change_count/1` in `lib/oli_web/live/projects/publication_details.ex` counts entries in the diff's changes map; `Utils.render_version/3` supplies version formatting. These behaviors should be reused rather than invented for Review.
  - **Remaining gap:** Review has no never-published/published/draft-excluded card, version or draft count for preview, or project latest-publication launch. Its current preview link targets the wrong content source for R-007.
  - **Verification and uncertainty:** Code and `test/oli_web/live/qa_logic_test.exs`/`test/oli_web/live/publish_live_test.exs` were inspected; no tests or browser interactions were executed. Child analysis must choose the minimal shared query/helper boundary and confirm how publication changes update the mounted card. Reuse existing subscriptions where applicable; do not create a new background synchronization mechanism.
- **Technical analysis:**
  - Load the latest published and working publications alongside Review state. Use the existing diff and version formatting semantics to derive the card state and total excluded change count; a card needs only the count, not the Publish table's row model.
  - Render three explicit states. Never published explains publication is required and offers Go to Publish. Published with no draft changes names the version and offers Open full course preview. Published with draft changes also displays the count and secondary Go to Publish.
  - Connect Open full course preview to the same S-012 project launch used by Publish, opening in a new tab with S-014's completed shell. No Review return origin is stored or propagated. S-012 checks that the associated section has completed its latest Publish-driven update. Surface its updating/failed response, including the common Reset Preview action in failed state for authorized project authors/admins, instead of opening stale content; launching does not refresh the section, and the card cannot override server readiness. Preserve Q10’s normal revision behavior for retained attempts.
  - Keep the QA state/event/subscription behavior and chart in place. Associate the card heading, provide textual version/count information, announce dynamic card changes without stealing focus, and announce that preview opens in a new tab. Exit preview closes the preview tab; the original Review tab stays open.
- **Prerequisite handoffs:** S-012's project launch operation and S-014's complete Full Course Preview banner/new-tab exit. These are actual usable handoffs; the published-version/diff APIs already exist.
- **Sizing analysis:** M; the new card/state integration and accessibility are the work, while version/diff data and QA machinery already exist.
