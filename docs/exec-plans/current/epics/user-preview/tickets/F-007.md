## Description

**Figma frames / prototype:** [Figma](https://www.figma.com/design/S8qAFhjjlnRyTHCg2Dyb8p/User-Preview-Overhaul?node-id=484-13490&t=5eBSflw0qUqbFcPl-1)

### User Need

As an author, I want to preview an entire published course with student-facing navigation, so that I can review its content, structure, and flow as a complete learning experience. I need to know which published version I’m viewing and whether draft changes are excluded.

### Acceptance Criteria

**Successful behavior**

- Update the **Review** page layout according to Figma, preserving existing review functionality and the chart.
- Add a **Full course preview** card with the following states:

| **Project state** | **Card content** | **Available actions** |
| --- | --- | --- |
| **Never published** | Explain that the project must be published before full course preview is available. | **Go to publish** |
| **Published, with no draft changes** | Identify the published version used for preview and explain that full course preview uses published content. | **Open full course preview** |
| **Published, with draft changes** | Identify the published version used for preview and show the number of draft changes excluded from it. | Primary: **Open full course preview**. Secondary: **Go to publish** |

- Selecting **Open full course preview** opens the latest published version on the **Learn** page.
- The preview provides student-facing course navigation, allowing authors to explore the entire published course.
- Use the existing template course-preview experience as the basis for this behavior **but update the exit preview to the primary button for contrast reasons.**
- Selecting **Go to publish** navigates to the project’s **Publish** page.
- On the **Publish** page, add a **Preview published course** action next to the latest publication version. It opens the same full course preview.

**Exceptions and safeguards**

- Full course preview is unavailable until the project has been published.
- Unpublished draft changes are excluded from full course preview.
- Both entry points open the same latest published version.
- Preserve the existing Publish table UI; the new table design shown in Figma is outside this scope.

### Accessibility Requirements

- **Keyboard:** All preview and publishing actions must be keyboard operable, follow a logical focus order, and have visible focus indicators. Course navigation within preview must remain keyboard accessible.
- **Semantics and labels:** Give the card a programmatically associated **Full course preview** heading. Use descriptive accessible names for actions and expose publication details and excluded draft counts as readable text.
- **Focus and navigation:** If preview opens in the same tab, manage focus to identify the destination page. If it opens in a new tab, communicate that behavior in advance. Ensure authors have a keyboard-accessible way to return to their authoring context.
- **State communication:** Communicate availability and excluded draft changes through text rather than color alone. If the card updates dynamically, announce the updated status without moving focus.

## Technical Guidance

### Suggested approach and ownership

Keep one shared preview section per project. Create it from the latest publication on first authorized launch; successful Publish operations subsequently queue its updates. Both Review and Publish use the same launch LiveView and student-only delivery experience. Existing attempts/progress remain during ordinary updates; active graded attempts may retain their older content revisions.

- [MER-6235](https://eliterate.atlassian.net/browse/MER-6235) owns section creation, its project association, markers, and Publish-driven updates.
- [MER-6236](https://eliterate.atlassian.net/browse/MER-6236) owns authorization, readiness checks, and the waiting LiveView.
- [MER-6237](https://eliterate.atlassian.net/browse/MER-6237) owns failed-state Reset Preview.
- [MER-6241](https://eliterate.atlassian.net/browse/MER-6241) applies the user supplied by [MER-6220](https://eliterate.atlassian.net/browse/MER-6220) to project enrollment, rendering, navigation, and activity requests. MER-6220 owns the reusable user resolver/reset/markers and enrollment-role rule, including upgrading existing preview-user enrollments when an author becomes an admin. Project enrollment uses instructor for admins and student/learner for regular authors; both retain the student-only Full Course Preview presentation.
- Publish and Review entry/shell work stays in their respective sub-tasks. Reuse [MER-6223](https://eliterate.atlassian.net/browse/MER-6223)'s student presentation, including My Notes and learner Class Notes; do not add an instructor selector.

### Existing code and important differences

`Blueprint.create_blueprint/5` creates resources from a publication. `Oli.Delivery.Sections.Updates.do_update/4` treats blueprint major updates as minor, so that path alone cannot guarantee hierarchy additions/removals. Reuse compatible update, external-tool initialization, and cache-invalidation code while applying the complete published structure.

`Publishing.publish_project/3` is shared by publishing entry points. Queue preview updates there transactionally with successful publication; the Publish UI's optional push to ordinary sections is insufficient. Reuse `Oli.Delivery.Updates.Worker` and Oban retries. Serialize conflicting creation/update/reset work so first-launch races lose no publication, obsolete jobs cannot regress or replace the section, and failed updates expose no partial completed state.

`Sections.get_current_publication/2` and update helpers provide useful checks, but `check_for_updates_in_progress/1` omits some retry/failure states. Oban prunes terminal jobs. Readiness must therefore use section/publication completion and applicable live jobs, not retained job history or broadcasts alone. A current, complete section is Ready; applicable queued/scheduled/executing/retryable work is Updating; stale/incomplete content with no such work is recoverably Failed.

### Launch, identity, and recovery

- Open one new tab containing the readiness LiveView. It automatically redirects to Learn in that tab when the server confirms readiness; no Check Again button. Recheck on reconnect and recover from missed notifications. Checks neither refresh content nor enqueue updates. Failed state exposes Reset Preview; Exit Preview closes the tab, assuming success, with no return tracking or fallback redirect.
- Keep actual-author authorization and real learner/SSO login unchanged. Existing template launch calls `UserAuth.log_in_user` for hidden users; do not reuse that login substitution. Preview requests must carry separately validated author/user/section context through navigation and activity calls. Concurrent learner/project/admin-preview tabs must not replace one another's identity. Invalid, revoked, or reset contexts cannot fall back to real learners or shared hidden users.
- Reset Preview is available to authorized project authors and admins only for the project's failed managed preview. Recheck access/state server-side, create a complete latest-publication replacement, switch the association atomically, and retire the old section. Existing `Sections.soft_delete_section/1` may support retirement. A new section naturally has fresh progress; no explicit attempt deletion is needed. Explain the shared effect and that existing tabs may need reopening.
- Reject retired-section contexts even through admin bypass. Failed reset preserves a recoverable association; concurrent resets/Publish/obsolete jobs cannot corrupt the replacement. Keep durable preview markers on current and retired sections, excluding ordinary sections and reusable products/templates. Cleanup is outside scope.

### Checks and limits

Cover first/repeated/concurrent launch, unpublished/unauthorized access, publication rollback, full hierarchy changes, retries and pruned-job recovery, automatic readiness navigation, and failed/concurrent reset. Preserve ordinary product/template behavior, real accounts, and normal preview progress. Do not add per-author sections, automatic progress reset, launch-time refresh, periodic content synchronization, or cleanup machinery.

`PageLifecycle.Graded.visit/1`, `PageContext.create_for_visit/4`, and `page_delivery_controller_test.exs` document retained-attempt revisions. `template_preview_test.exs` and `products_controller_test.exs` cover reusable enrollment/authorization behavior. Choose the smallest schema, locking, and request-context changes that satisfy these requirements; component names and transport are not fixed implementation contracts.
