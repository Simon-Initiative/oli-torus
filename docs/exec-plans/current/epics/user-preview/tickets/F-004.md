## Description

**Figma frames / prototype:** [Figma](https://www.figma.com/design/S8qAFhjjlnRyTHCg2Dyb8p/User-Preview-Overhaul?node-id=484-13892&t=5eBSflw0qUqbFcPl-1)

### User Need

As an author, I want to preview the current page in an interface that reflects the current student UI, so that I can assess its appearance. I need the preview to clearly communicate that it represents a single page and provide an accessible way to exit at any time.

### Acceptance Criteria

**Successful behavior**

- Update the existing preview action to use the secondary button style with the label **Page preview**.
- Opening page preview displays the page using the current NG student UI styling.
- Update the preview banner to match the Figma designs and clearly identify the experience as **Page preview**.
- Keep the banner visible at the top of the viewport as the user scrolls.
- Provide an exit control in the banner that returns the author to the authoring page they were previewing.

**Exceptions and safeguards**

- Exclude course navigation elements, including page navigation, the back button, and the course outline.
- Exclude DOT and notes.
- Keep the preview banner and exit control available throughout the page, including on long pages.

### Accessibility Requirements

- **Keyboard:** The **Page preview** action and exit control must be keyboard operable and have visible focus indicators.
- **Semantics and labels:** Give the preview banner a descriptive accessible label. The exit control’s accessible name must clearly communicate that it returns to authoring.
- **Focus:** On entering preview, place focus at a logical starting point that identifies the page-preview context. On exit, restore focus to the **Page preview** button in authoring.
- **Sticky banner and reflow:** Ensure the banner does not obscure content or focused elements. At increased zoom and narrow viewport widths, its text and exit control must remain readable and operable.

## Technical Guidance

### Size and feasibility

- **Size:** XL (more than 10 focused engineering days).
- **Single-engineer feasibility:** Feasible in stages. Sharing delivery presentation without requiring a learner account affects basic and advanced rendering and needs substantial regression coverage.
- **Estimate basis:** An engineer familiar with Torus; includes implementation and verification, excludes dependency/review waiting time. This is a planning estimate, not a delivery commitment. Story effort includes any sub-tasks; do not add the Story and sub-task estimates together.

### Suggested approach

Render author Page Preview through the same delivery layouts and page components used by learners, so delivery UX changes also appear in preview. Adapt those components to accept page/display data and flags for available controls. Keep learner loading, enrollment, and attempt creation in the normal delivery callers; an authorized author must be able to render preview without a database-backed learner account.

Keep `ResourceController.preview/2`, `AuthoringResolver`, and the nonpersistent preview activity bridge. They already resolve working content and support activity interactions. Replace duplicated basic and advanced preview presentation with shared components, retaining only the small wrappers needed for their different runtime inputs. Do not mount the learner lifecycle just to obtain the UI or build a general rendering framework.

### Code to inspect

- `lib/oli_web/templates/resource/page_preview.html.heex` duplicates page layout, spacing, banner, references, and navigation.
- `lib/oli_web/components/layouts/student_delivery_lesson.html.heex`, `page.html.heex`, `lib/oli_web/components/delivery/layouts.ex`, `Student.Utils.page_header/1`, `references/1`, and `LessonLive` contain the corresponding delivery presentation. Account-dependent controls need explicit display inputs or omission in author preview.
- `resource/advanced_page_preview.html.heex` and `page_delivery/advanced_delivery.html.eex` duplicate the advanced delivery wrapper. Share applicable mounting/presentation code while retaining `app_params`, `previewMode`, `previewSequenceId`, and adaptive sequence behavior.
- `editor_live.ex` and `PageEditor.tsx` already open a named preview window. Keep the editor open and restore its launch-control focus on exit, using a safe authoring fallback if the opener is unavailable.

### Constraints and checks

- Working/unpublished content, selection errors, supported evaluation/hints/reset, and adaptive sequence selection must still work. Do not silently substitute student delivery or change publications.
- Hide course navigation, previous/next, back, outline, DOT, and notes as required above. Keep the sticky banner and exit usable without obscuring content/focus.
- Rendering creates no learner/hidden-user account, section, enrollment, persisted learner attempt, or progress. Author/project authorization remains mandatory.
- Verify both preview types and ordinary delivery, including an author with no learner account. Update tests that currently expect preview previous/next links; retain selection-error and `previewSequenceId` coverage. Check scrolling, zoom/reflow, keyboard operation, and cross-window return focus in the browser.
- Preserve other consumers of the advanced template. No broader container, account-menu, or delivery-lifecycle redesign is included.
