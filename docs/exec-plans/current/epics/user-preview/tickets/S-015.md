# S-015: Manage and reset the author-linked preview user

- **Status:** Approved and pending creation
- **Qualification:** Qualified. Subagent code inspection establishes the missing preview-user association, account-settings action, durable user classification, and project-preview identity integration. S-016 reuses the same identity for admin section previews. Q11 requires a dedicated author-linked preview user, created on first use and replaced by explicit Reset Preview User.
- **Lane:** D, second; S-012 → S-015 → S-016 → S-014 → S-013; S-016 → S-014 is scheduling only.
- **Ticket:** pending.

## Description

Give each author one dedicated preview user, reused across project previews and authorized admin section previews, with Reset Preview User in account settings.

- **Requirements:** [MER-6158](https://eliterate.atlassian.net/browse/MER-6158), R-010, R-011, R-007, R-008. Full requirements are in the epic ticket.
- **Scope:**
  - Create and link the user lazily on first supported use, through an association distinct from normal learner/SSO accounts.
  - Reset creates a fresh generated user and atomically replaces the current link. New progress follows from the new user ID; keep old records and shared project sections intact.
  - Mark current and superseded author-owned preview users so database queries and remaining legacy fallback selection can distinguish them.
  - Use the selected user consistently throughout project Full Course Preview while preserving actual-author authorization and normal learner authentication. S-016 integrates admin section entries.
- **Technical approach:** Reuse existing generated-user and account-settings patterns with a distinct current preview-user association and durable purpose/ownership information. Integrate the resolver with S-012’s launch/session boundary and activity paths; exact schema and component choices remain provisional. Add no cleanup or explicit progress-clearing operation. Proposed implementation details are provisional; required behavior and binding constraints remain mandatory.
- **Acceptance criteria:**
  - **Positive:**
    - **AC1:** An authenticated author can select Reset Preview User in their own account details/settings and receives accessible success or failure feedback.
    - **AC2:** Successful reset creates a fresh marked preview user and atomically links it as that author’s current preview user. Future project Full Course Preview launches use it across projects with newly established preview enrollments as needed; S-016 consumes the replacement for subsequent admin section previews.
    - **AC3:** Reset naturally starts fresh progress under the new user ID; it does not recreate shared preview sections or clear stored attempts/progress. Other authors’ current preview-user associations remain unchanged. For an admin, replacing this same user also starts fresh progress in subsequent admin section previews through S-016.
    - **AC4:** A direct database query identifies current and superseded generated preview users after repeated resets and distinguishes author-owned preview users from legacy shared identities. Real learner accounts are excluded; S-016 can exclude superseded author-owned records from shared fallback without relying on the current author link.
    - **AC5:** Project preview rendering, navigation, activity requests, and exit use the intended identity while retaining actual-author permissions and preserving the author’s ordinary learner/SSO link and authentication/session behavior.
    - **AC6:** First supported project/admin preview use creates/links one dedicated preview user when absent; subsequent launches reuse it until explicit reset. S-016 integrates admin entries with the same resolver. Concurrent provisioning/reset calls leave one current association, and failed reset preserves the prior association.
  - **Negative:**
    - **AC7:** Forged author/user IDs cannot reset another author’s association or grant access to an unauthorized project/section. Generated preview identities do not enter normal learner/SSO account-link flows. Provisioning failure cannot silently fall back to real learner or shared section-hidden identities.
    - **AC8:** Ordinary learner progress, regular instructors’ own identities, and author Page Preview/Question Preview remain unaffected. Admin previews change only through S-016’s unified identity integration. Shared project-section Reset Preview remains a separate failed-state operation.
    - **AC9:** No cleanup job, old-user deletion, retention mechanism, or explicit progress-clearing operation is introduced. Superseded users remain marked for later cleanup.
- **Prerequisites:** S-012.
- **Size:** XL.
- **Sub-tasks (in order; both required for Story acceptance):**
  - **S-015a — Preview-user ownership, markers, and reset.** Add the distinct current association, durable user marker, lazy resolver shared with S-016, atomic fresh-user reset, and accessible own-account settings action. Verify ordinary account-link compatibility, current/superseded classification, authorization, concurrency, and failure (AC1–4, AC6/7/9).
  - **S-015b — Full Course Preview identity integration.** Apply first-use dedicated-user provisioning and the selected preview user throughout project preview launch, rendering, activity requests, and exit. Verify cross-project fresh progress, authorization, real-session preservation, and isolation from other preview contexts (AC2/3, AC5–8).
- **Feature flags:** None. S-014 exposes project Full Course Preview after the identity integration is available.

- **Scope analysis:** Add first-use provisioning, the self-service account action, current author→preview-user association, generated-user marker, atomic fresh-user replacement, and integration across project Full Course Preview launch/rendering/activity/exit paths. Existing project access remains authoritative. Expose the same current-preview-user resolver to S-016; do not create a separate admin preview-user model. Preserve normal learner/SSO links, regular instructor accounts, and separate author Page Preview/Question Preview behavior. S-016 owns the approved admin preview integration, including affected shared-admin fallbacks. Cleanup and deletion are excluded.
- **Sources and design:** Operator requirement for Reset Preview User and queryable preview records. Existing Author Account Settings Details surface at `/authors/settings` supplies the UI context. N/A for a new Figma frame; use existing account-settings components and accessibility patterns.
- **Analysis:**
  - **Existing behavior:** `lib/oli_web/live/author_settings_live.ex` provides authenticated author Details and settings events. `lib/oli/accounts/schemas/author.ex` has many linked users through `users.author_id`; `lib/oli_web/views/authoring_view.ex` uses a single-result author-linked-account lookup. `Accounts.link_user_author_account/2` serves normal learner/SSO linkage. Existing synthetic-user creation and enrollment in `lib/oli/delivery/sections.ex` provide reusable patterns.
  - **Remaining gap:** There is no current author-specific preview-user association or reset action. Repeatedly attaching preview users through the normal author linkage can make that existing single-result lookup ambiguous. The generic hidden flag cannot classify preview records safely for later queries. `TemplatePreview.resolve_launch_identity/2` converts any hidden current user into a shared section fallback; it must not discard the project preview user. `UserAuth.log_in_user/3` replaces the normal learner token, and current hidden-user exit does not restore a prior learner login. These session/runtime implications require explicit integration.
  - **Verification and uncertainty:** Targeted subagent/coordinator code inspection only; no tests or resets performed. Q11 settles first-use provisioning; no product decision remains open for this Story. Child design must settle the smallest association and scoped identity/session boundary, then verify controller/LiveView/activity API consistency and preservation of real learner/author authentication. This is project-preview work, not a general authentication redesign.
- **Technical analysis:**
  - **Binding constraints:** Reset only the requesting author’s preview-user association. Create a fresh generated preview user rather than clear progress or recreate project sections. Preserve real learner/SSO linkage, author authentication, and normal course progress. Project access is checked independently of the generated user.
  - **Ownership and classification:** Prefer a distinct current association such as `authors.preview_user_id`; do not add successive preview identities to normal `users.author_id` linkage. Persist explicit preview-purpose/ownership information at creation and retain it after replacement. It must identify current and superseded author-owned preview users so S-016’s legacy shared fallback can exclude them; a current-association lookup alone is insufficient. A purpose field such as `users.preview_purpose` can provide both cleanup identification and that distinction; exact schema remains provisional. Expose an owned-preview-user resolver to S-016 for authorized admin use. Hidden-user behavior may still be useful, but hidden alone is not the classification. Do not mark real learner accounts as preview users merely because they enter preview.
  - **Reset operation:** Use existing authenticated account-settings event/request patterns and normal synthetic-user creation foundations. Create the new user and swap the association atomically; failed reset retains the previous link. Serialize concurrent resets so one current association remains. Keep old generated users identifiable; add no deletion, progress-clearing, retention, or cleanup process.
  - **Project preview integration:** Consume S-012’s authorized launch/readiness/session contract. Resolve or create the author’s dedicated preview user before entering project Full Course Preview, enroll it in each authorized project preview section as needed, and use it consistently for rendering, attempts, and activity requests. Preserve actual author authorization and normal learner session/identity through entry and tab-close exit. Closing the preview tab leaves the reusable preview user and project section intact and requires no tracked return URL or fallback redirect. Reopening preview after reset uses the new link; existing tabs may need to be reopened. S-016 supplies the admin section enrollment/context adapter; keep regular instructor and separate author-page/question contexts unchanged.
  - **First-use policy:** Under Q11, every author uses a dedicated preview user for project Full Course Preview. Create and link it lazily on first use, then reuse it across projects until explicit Reset Preview User replaces it. A failed provisioning operation must not fall back to a real learner account or the shared section-hidden identity. S-016 reuses this same lazy resolver for an admin’s first section preview; whichever supported entry is used first creates the current association. Legacy behavior outside the approved admin integration remains separate.
- **Prerequisite handoffs:** S-012’s project Full Course Preview section, launch/readiness, and session contract for final identity integration. Account association/reset work can start independently. Exit handoff: the current author-linked preview-user resolver/reset contract consumed by S-016 and the project preview identity contract consumed by S-014/S-013.
- **Sizing analysis:** XL; user creation/linkage is bounded, but identity propagation across LiveView/controller/activity APIs and preservation of real sessions require coordinated work.
