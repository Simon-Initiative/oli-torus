## Description

> Provide one dedicated preview user per author, with reusable first-use provisioning and an accessible Reset Preview User action in account details/settings. Project Full Course Preview and authorized admin section previews consume this shared capability through their own Story integrations.

- **Scope:**
  - Add a current author-to-preview-user association distinct from normal learner/SSO account links.
  - Expose a resolver that lazily creates the dedicated user when absent and reuses it until explicit reset.
  - Reset creates a fresh generated user and atomically replaces the association. Keep previous users, attempts/progress, and shared project sections intact.
  - Mark current and superseded preview users with durable purpose/ownership information so direct database queries and legacy shared-user queries can distinguish them from real users and shared identities.
  - Provide the account settings action independently of project section creation, publication updates, or preview launch readiness.
- **Acceptance criteria:**
  - **Positive:**
    - AC1: An authenticated author can select Reset Preview User in their own account details/settings and receives accessible success or failure feedback.
    - AC2: Successful reset creates a fresh marked preview user, atomically links it to the requesting author, and makes it the result of subsequent resolver calls.
    - AC3: Reset changes the user identity without clearing stored attempts/progress, recreating shared sections, or changing another author’s association. Consumers obtain fresh progress through the new user ID.
    - AC4: Direct database queries identify current and superseded generated users after repeated resets and distinguish author-owned preview users from legacy shared identities and real learner accounts.
    - AC5: Resolving or resetting a preview user preserves actual-author authentication, normal learner/SSO linkage, and ordinary course progress.
    - AC6: Concurrent first-use provisioning/reset calls leave one current association. Existing users are reused until reset; failed reset preserves the prior association.
  - **Negative:**
    - AC7: Forged author/user IDs cannot reset or resolve another author’s association. Provisioning failures do not fall back to real learners or shared section-hidden identities. Consumers must separately authorize the requested project or section.
    - AC8: Generated identities do not enter normal learner/SSO linking flows. Ordinary instructor accounts and separate author Page Preview/Question Preview behavior remain unaffected. Section Reset Preview remains a separate operation.
    - AC9: No cleanup job, old-user deletion, retention mechanism, or explicit progress-clearing operation is introduced. Superseded users remain marked for later cleanup.

## Technical Guidance

### Suggested approach

Keep the author's current preview-user association separate from normal learner/SSO linkage. `authors.preview_user_id` is one option; do not add successive generated identities to normal `users.author_id` linkage. Store purpose/ownership markers independently so superseded users remain identifiable after reset. Exact fields are engineering decisions.

Reuse `lib/oli_web/live/author_settings_live.ex`, the author schema, and synthetic-user creation in `lib/oli/delivery/sections.ex`. Preserve `Accounts.link_user_author_account/2`'s existing behavior. Create the user and replace its association atomically; coordinate concurrent first-use/reset calls and retain the old association on failure.

The preview user is a persistent delivery identity, never a logged-in account. Consumers pass its struct or ID to delivery within authorized preview context, keeping real authentication separate.

The resolver returns the existing preview user or creates one on first use. Reset creates a replacement without clearing attempts, deleting old users, or recreating shared sections. Project integration belongs to [MER-6241](https://eliterate.atlassian.net/browse/MER-6241); admin section and author/admin template integration belongs to [MER-6225](https://eliterate.atlassian.net/browse/MER-6225).

Use instructor section enrollments for admin-owned preview users and student/learner enrollments for regular authors' preview users. This lets admins use both Instructor View and Student Preview in course sections without changing user identity. These are section roles, not global administrator permissions.

When an author becomes an admin, upgrade their current preview user's existing section enrollments to instructor, if a preview user exists. Preserve that user and its progress; do not create a user merely because the author was promoted. Subsequent enrollments, including after Reset Preview User, use the author's current role. Apply this through the author role-change flow in `lib/oli/accounts.ex`; launch integrations use the same role rule when enrolling users. Full Course Preview still uses its student-only presentation.

Implement and verify account settings, the resolver/reset capability, ownership markers, and the enrollment-role rule directly in this Story. Project and admin/template integrations consume these capabilities; their launch/session flows are not prerequisites for completing this Story.

Verify regular-author and admin enrollment roles, promotion with and without an existing preview user, and reset after promotion, alongside the own-account, concurrency, failure, classification, and accessible-feedback criteria above. Preserve real authentication/accounts and add no cleanup work.

## QA Misc

### Suggested QA Steps

**Setup:** Use two regular authors, an admin, and an author linked to a real learner account with existing progress. Developer-assisted resolver calls, enrollment fixtures, database inspection, and failure/concurrency tests allow this Story to be verified before launch integrations are complete.

1. Resolve a preview user twice for the same author, then for the other author. Confirm first use creates one marked user, repeat use returns it, and authors have distinct users separate from normal learner/SSO links.
2. In account details/settings, select Reset Preview User. Confirm accessible success feedback and a new current user returned by subsequent resolver calls. Repeat; confirm previous users/progress and shared sections remain intact, and another author's association is unchanged.
3. Check enrollment roles for a regular author and admin: learner and instructor respectively, with no global admin grant. Promote an author with an existing preview user; confirm the same user's existing enrollments become instructor without losing progress. Promote one without a preview user; confirm promotion alone creates none. Reset after promotion and confirm new enrollments follow the admin role rule.
4. Inspect database queries after repeated resets. Confirm current and superseded generated users remain identifiable by purpose/owner and distinguishable from real learners and legacy shared users.
5. Simulate concurrent first-use/reset calls and provisioning/reset failures. Confirm one current association remains, failed reset retains the previous association, and failures never substitute a real learner or shared user.
6. Attempt to resolve/reset another author's user using forged IDs or an unauthenticated request. Confirm denial. Verify real login, normal learner/SSO linkage, and ordinary progress remain unchanged throughout; no preview-user authentication token is created.
7. Operate Reset Preview User by keyboard and screen reader. Confirm its name, visible focus, and success/failure feedback are accessible. Verify ordinary instructor accounts and separate Page/Question Preview remain unaffected.
