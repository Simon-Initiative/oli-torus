## Description

## Scope

Provide the authorized project launch and readiness LiveView, with automatic same-tab Learn navigation when ready and the approved isolated preview-request context.

## Acceptance criteria

### Positive

- Authorized launch resolves the managed section and classifies Ready, Updating, or Failed from current server state.
- The shared LiveView automatically enters Learn in the same preview tab when ready and supports reconnect/missed notifications as specified below.
- Failed-state UI uses the shared reset action; initial-creation failure prevents launch and gives an actionable failure response.

### Negative

- Unpublished, unauthorized, stale, or incomplete previews cannot enter Learn. Launch checks do not refresh section content or enqueue an update for an existing section.
- No return-origin tracking or close-failure redirect is introduced. Opening/closing preview preserves real authentication and saved progress.

## Technical Guidance

Use MER-6235’s project association and update state. Authorize the project before creation or launch; reject never-published projects. Check currentness/completion without rebuilding an existing section. Expose MER-6237's recovery action when failed and provide the validated launch context to project identity integration. Preserve compatible product/template behavior. The sections below define the approved LiveView behavior, session preservation, and readiness classification.

Use the parent [F-007](https://eliterate.atlassian.net/browse/MER-6217) for shared feature requirements, design sources, and code evidence. This sub-task is complete when its scoped acceptance criteria above and the applicable shared constraints are satisfied.

### Show readiness in a LiveView

Both Review and Publish open the shared project launch URL in a new tab, leaving the authoring tab intact. Render the readiness view as a LiveView. Check readiness before entering Learn: a ready preview redirects immediately to Learn in the same tab; Updating or Failed shows the current status instead of stale course content.

- **Updating:** Show “Preview is updating. You will be taken to the course when it is ready.” Automatically recheck readiness and redirect to Learn in the same tab once the server confirms the current preview is ready. Do not provide a Check Again button.
- **Failed:** Explain that preview could not be prepared and provide the existing **Reset Preview** action with its shared-progress explanation. After successful reset, recheck readiness and automatically enter Learn when ready. A failed reset keeps the failure message and recovery action available. If another authorized action recovers the preview, the open LiveView reflects the new state and redirects when ready.
- **Exit:** Both status states provide **Exit Preview**, which closes the preview tab using the approved close-tab behavior. No return URL or close-failure redirect is added.

Use the existing server readiness operation as the source of truth. A simple approach is a periodic readiness check while the LiveView is connected, optionally accelerated by existing update broadcasts. Broadcasts alone must not establish readiness or be the only means of detecting completion. Recheck on mount/reconnect and after reset, and revalidate authorization and the current managed section/publication before redirecting. Keep checks bounded to the connected view, avoid overlapping checks, and stop them when the view exits or redirects. Checks do not enqueue updates, refresh section content, or create new tabs. Exact timing and notification wiring remain implementation decisions.

- **Acceptance:** From either Review or Publish, a pending update opens one LiveView in a new tab. When the update completes, it automatically redirects to Learn in that tab without another user action. Completion before subscription/mount, missed broadcasts, and reconnect cannot leave the view waiting indefinitely.
- **Acceptance:** The view reflects Updating and Failed transitions while retaining exit/recovery controls. Announce status changes without moving focus or repeatedly announcing unchanged status; navigation to Learn identifies the destination normally. Keyboard users can operate reset and exit, and reset exposes its busy state and prevents duplicate submissions. A temporary readiness-check failure shows connection/check feedback and retries automatically; it does not claim the section is ready or permanently failed without a server result. Revoked authorization prevents redirect and further preview access.

### Preserve the signed-in accounts

Opening Full Course Preview must not log the browser in as the generated preview user or replace its learner authentication token. Keep the signed-in author and any real learner account unchanged. Use the author-linked preview user only for requests belonging to the authorized preview. Closing the preview tab requires no logout or restoration of an earlier account.

The existing `ProductsController.preview_launch/2` calls `UserAuth.log_in_user/3` for a hidden user, and `UserAuth.auto_enroll_admin/2` writes a generated user's token into the browser session. Those identity-switching operations are not reusable for this launch. Reuse compatible section and enrollment operations while adapting identity resolution before delivery loads enrollment, page state, or attempts.

A credible approach is to carry a server-validated preview context with preview navigation and activity requests, rather than save one browser-wide active preview identity. Bind that context to the authenticated author, the current author-to-preview-user association, and the authorized section/project. Recheck those relationships at the relevant request boundaries. The context identifies preview requests; it does not select Instructor View versus Student Preview, which remains route-derived. The exact transport and helper structure remain implementation decisions; an existing Phoenix-signed value carried with the preview's links and requests is one option.

- **Acceptance:** With a real learner tab already open, launch project preview, navigate and interact in both tabs, and close preview. The learner tab keeps its original account and progress; preview activity belongs only to the preview user. A launch by an author without a learner login must not create a browser-wide learner login.
- **Acceptance:** Opening another project preview does not replace the first preview's section or identity context. Refresh and LiveView reconnect preserve each valid context. Invalid or superseded preview contexts are rejected without falling back to the real learner or a shared hidden user.

### Classify readiness without retained job history

After checking the current managed section and latest publication, apply these outcomes:

- **Ready:** The latest publication and structural update are complete. A retained completed-job record is not required, and unrelated historical failures do not block launch.
- **Updating:** An applicable update is queued, scheduled, executing, or retryable and can still bring this managed section to the required publication.
- **Failed:** The section is stale or its update is incomplete, and no applicable live update remains. Cancelled/discarded jobs and missing or pruned terminal job records fall into this outcome. Return the same recoverable failed response used by Reset Preview rather than displaying Updating indefinitely.

Check section association, publication completion, and applicable jobs consistently with the Publish/update/reset operations. Jobs for retired sections and obsolete publications must not be treated as progress toward the current launch. Reuse existing persisted state where sufficient; minimal additional completion/failure state is an implementation option only if existing state cannot distinguish these outcomes reliably. Launch still performs no rebuild or refresh.

- **Acceptance:** A stale or incomplete preview with no applicable live job reports Failed after cancellation, exhausted retries, or pruning of the terminal job. A queued/scheduled/executing/retryable applicable job reports Updating. A complete current section reports Ready after completed-job pruning. Cover concurrent Publish/update/reset transitions without exposing partial content or offering reset solely because of an inconsistent read.
